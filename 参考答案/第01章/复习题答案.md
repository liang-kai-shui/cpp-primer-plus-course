## 4.1 C++ 的三个思想来源分别是什么？每一个给 C++ 带来了什么特征？

**参考答案**

| 思想来源 | 给 C++ 带来的特征 |
|---|---|
| **C 语言**（过程性 / 结构化编程） | 高效、贴近硬件、可直接操作内存。C++ 完整继承了 C 的语法和运行效率，「C++ 是更好的 C」这一半就来自这里 |
| **Simula 67**（面向对象编程） | 类（class）、对象、封装、继承、多态。C++ 最初的名字就叫「C with Classes」 |
| **泛型编程**（模板机制，思想可追溯到 Ada / CLU / ML 等语言） | 模板（template）、STL 容器与算法。「写一次，适配任意类型」，同一份代码能处理 `int`、`double`、自定义类 |

一句话概括：**C 给了 C++ 效率与底层能力，Simula 67 给了它面向对象的抽象能力，模板给了它泛型复用的能力。**

**原始作答记录**

> 过程性思想来自 C，面向对象来自 Simula 67，泛型编程来自 不知道

**核对结果**

- 「过程性来自 C」——✅ 对。
- 「面向对象来自 Simula 67」——✅ 对。更细的说法是「Simula 67（或写作 Simula）」，两种写法教材里都出现过。
- 「泛型编程来自 不知道」——❌ 没答出来。

> **订正说明**：原答案泛型编程一栏写的是「不知道」，正确应为「来自模板（template）机制，其思想可追溯到 Ada、CLU、ML 等语言」，因为它给 C++ 带来的正是 **template 模板**，以及建立在其上的 **STL（标准模板库）**——同一份代码可以适配任意类型，这是 C++ 区别于 C 的第三大支柱。
> 此处建议对照教材附录 J（p933）核对措辞，不同版本教材对「泛型来源」列举的语言可能略有差异。

## 4.2 从 `demo.cpp` 到 `demo.exe` 有哪四步？每步用什么命令、产出什么文件？

**参考答案**

| 步骤 | 名称 | 命令 | 产出 |
|---|---|---|---|
| ① | **预处理** | `g++ -E -std=c++17 demo.cpp -o demo.i` | `demo.i`（展开后的源代码文本） |
| ② | **编译** | `g++ -S -std=c++17 demo.cpp -o demo.s` | `demo.s`（汇编代码） |
| ③ | **汇编** | `g++ -c -std=c++17 demo.cpp -o demo.o` | `demo.o`（目标文件，机器码） |
| ④ | **链接** | `g++ demo.o -o demo.exe` | `demo.exe`（可执行文件） |

> 记忆要点：**E → S → c → 链接**。
> `-E` 只做预处理；`-S` 产出汇编；`-c` 产出目标文件；不加任何字母就是一路做完再链接。

**原始作答记录**

> 预处理：g++ -E　编译：g++ -S　汇编：g++ -c　链接：g++ main.o -o main.exe

**核对结果**

- 四步的**名字**全对，四个关键选项 `-E` / `-S` / `-c` 也全对，顺序正确。✅
- 但**少了「产出什么文件」**：题目问了两件事（命令 + 产出文件），答案只答了命令。
- 链接一步的文件名写成了 `main.o` / `main.exe`，与本题的 `demo.cpp` 对不上。

> **订正说明**：原答案的链接命令写的是 `g++ main.o -o main.exe`，本题的源文件叫 `demo.cpp`，正确应为 `g++ demo.o -o demo.exe`，因为 `main.o`/`main.exe` 是另一个文件名，跟本题的 `demo.*` 不是一回事；另外原答案漏答了每步的产出文件，正确应为 ①`demo.i` ②`demo.s` ③`demo.o` ④`demo.exe`，因为题目明确问了「产出什么文件」，答全才算完整。
>
> ⚠️ 补充一个容易混的点：编译器的 `-S` 选项名字看着像「Source」，但它产出的是**汇编**（`.s`）；`-c` 看着像「compile」，但它其实是**只编译不链接**，产出**目标文件**（`.o`）。名字和实际含义是错位的，别按字面猜。

## 4.3 为什么 `#include` 后面**不写**分号？

**参考答案**

因为 `#include` 是**预处理指令**，不是 C++ 语句。

- 第①步预处理时，编译器**根本还没开始真正编译 C++ 代码**，它先把 `#include <iostream>` 这一行**整行替换成 `iostream` 头文件的全文内容**（相当于把那个文件的内容复制粘贴到这一行）。
- 预处理指令是**按行**识别的、以 `#` 开头的命令，一行就是一条指令，**它的结束标志是换行，不是分号**。
- 相比之下，C++ 语句（如 `int a = 1;`）必须用分号结尾，因为 C++ 允许语句跨行书写，编译器需要一个明确的结束符号。
- 如果在 `#include` 后面加了分号，预处理把它替换成头文件全文以后，那个多出来的 `;` 就孤零零地留在代码里。GCC 会给出警告 `extra tokens at end of #include directive`（该指令末尾有多余的记号）。**它通常不会报错**（见错误分类实验 C），但这是错误写法，换一个编译器或换一个标准就可能真的报错。

**原始作答记录**

> `#` 是预处理命令，相当于导入工具包

**核对结果**

- 「`#` 是预处理命令」——✅ 方向对。
- 但没答到题目真正问的点：「为什么**不写分号**」。

> **订正说明**：原答案写的是「# 是预处理命令，相当于导入工具包」，只说了 `#include` 是什么，没有回答「为什么不能写分号」；正确应为「因为它是**预处理指令**，第①步预处理时会把这一行**整行替换成头文件全文**，预处理指令以**换行**为结束标志而不是分号，**分号是 C++ 语句的结束符**，两者属于不同的层次」。因为题目问的是「为什么」，必须说到「替换成头文件全文」和「结束符是换行」这两层机制才算答对。

## 4.4 「头文件」和「库」分别扮演什么角色？打个比方说明。

**参考答案**

| | 头文件（header file） | 库（library） |
|---|---|---|
| 里面装的是什么 | **声明**：函数原型、类定义、宏、模板等「说明书」 | **定义**：已经编译好的机器码（目标文件 / `.lib` / `.a` / `.dll`） |
| 什么时候用 | **编译期**（第①②步）需要它，编译器靠它检查你的调用写得对不对 | **链接期**（第④步）需要它，链接器靠它把真正的机器码接进你的程序 |
| 典型例子 | `iostream`、`string`、`vector` | 标准库 `libstdc++`、`libc`、Windows 的 `.dll` |
| 少了它会怎样 | 编译错误：`'cout' was not declared` 之类 | 链接错误：`undefined reference to ...` |

**打个比方**（餐厅的比喻）：

- **头文件 = 菜单**。上面写着「本店有这道菜、叫什么名字、什么口味、几个参数」。你看着菜单就能点菜，也就能检查自己点得对不对。但菜单不能吃。
- **库 = 后厨**。真正把菜做出来的是厨房。你不需要知道厨师怎么做，只要菜单上的名字对得上，厨房就能把菜端上来。
- 所以：**菜单（头文件）写错了 → 点菜时就被拦下来 = 编译错误**；
  **后厨（库）里没有这道菜 → 点了半天端不上来 = 链接错误（undefined reference）**。

> 一句话：**头文件管「编译期能不能通过」，库管「链接期能不能接上」。** 这也正是判断编译错误和链接错误的分界线（呼应 4.5 题）。

**原始作答记录**

> 头文件是一个具体的文件，里面装着库，比方想不出来

**核对结果**

- 「头文件是一个具体的文件」——✅ 对。
- 「里面装着库」——❌ 不准确。头文件里装的是**声明**，不是库本身。它只是告诉编译器「库里有这些东西」，真正的机器码在别处。
- 「比方想不出来」——❌ 没答。

> **订正说明**：原答案写的是「头文件里面装着库」，正确应为「头文件里装的是**声明**（函数原型、类定义等），**库**里装的才是**编译好的机器码**」；因为头文件是**文本**，链接器没法直接拿它来生成程序，它只负责在编译期让编译器认识这些名字，真正的机器码由第④步从库里取。比方可以打「头文件=菜单，库=后厨」。
> 此处建议对照教材附录 J（p933）核对，官方答案的比方可能与上面不同，但「声明 / 定义」这一层区分是一致的。

## 4.5 拿到一个报错，你怎么判断它是编译错误还是链接错误？两者的排查方向有什么不同？

**参考答案**

**第一句话先问自己：「有 exe 吗？」**

| 现象 | 判断 | 报错特征 | 排查方向 |
|---|---|---|---|
| **没有 exe**，报错里有 `error:` + `文件名:行:列` | **编译错误** | `error: expected ';' before 'return'`、`'x' was not declared`、`expected primary-expression` | 去看**报错的行号处**。注意 GCC 报的行号常指向「发现错误的地点」而不是「错误本身」——看到 `expected ';' before X`，先去查 **X 的上一行末尾** |
| **没有 exe**，报错里有 `undefined reference` / `ld` / `collect2` | **链接错误** | `undefined reference to 'add(int, int)'`、`collect2.exe: error: ld returned 1 exit status` | 去查**函数有没有定义**、**定义所在的那个 .cpp 有没有加进编译命令**（`g++ a.cpp b.cpp -o app.exe`）、**库有没有用 `-l` 链接上** |
| **有 exe**，但结果不对 / 中途崩了 | **运行时错误** | 编译器一声不吭，退出码非 0 | 去看**退出码**（0 = 正常，非 0 = 出问题了）、打日志、上调试器、写测试。这类错误编译器帮不了你，因为值要到运行时才确定 |

**两个最实用的抓手：**

1. **看有没有 `.o` 被生成出来**。编译（①②③）全过了才轮到链接，所以在链接报错里你会看到形如 `C:\Users\...\Temp\xxxx.o` 的临时目标文件路径——它出现，说明前面三步都成功了，问题只在最后一步。
2. **看报错者是谁**。报错主体是 `g++`/`cc1plus` → 编译器；报错主体是 `ld`/`collect2` → 链接器。

**原始作答记录**

> 不清楚

**核对结果**

- ❌ 未作答（如实写了「不清楚」，没有硬编——这一点是对的，看不出来就是看不出来）。

> **订正说明**：原答案写的是「不清楚」，本题空缺；正确应为「先看**有没有生成 exe**：没有 exe 且报错带 `error:` + `文件:行:列` 的是**编译错误**（去看行号处或上一行），没有 exe 且报错带 `undefined reference` / `ld` / `collect2` 的是**链接错误**（去查函数定义和参与编译的文件），有 exe 但结果不对或崩溃的是**运行时错误**（去看退出码、写测试）」，因为这三类错误分别发生在第①②③步、第④步、和第④步之后，报错主体和关键词完全不同，是完全可以分开的。
>
> 这条是本章最该掌握的一条，建议对着 `参考答案/第01章/错误分类实验-答案.md` 的「你现在应该建立的条件反射」一节再读一遍。

## 4.6 为什么说"编译通过"完全不代表"程序是对的"？举一个你自己代码里的例子。

**参考答案**

因为编译器**只检查语法和类型**，它检查不了**语义和逻辑**。

- 编译器能管的：漏分号、拼错名字、类型不匹配、函数没定义。
- 编译器管不了的：数组越界、除以 0、整数溢出、忘了初始化、循环边界差一、算法本身写错。这些都叫**未定义行为（UB）或逻辑错误**——标准里说「这种情况下的行为不做任何保证」。
- 根源在于：很多值要到**运行时**才确定。例如 `int a = 10; int b = 0; cout << a / b;`——编译器编译时**不知道** `b` 是 0，它没法预知。
- 更危险的是：这类错误可能**不崩溃、退出码 0、输出看着还挺正常**，于是你以为程序没问题，直到错误的数据被写进了数据库。

**例子（结合本课做过的实验）**

```cpp
int a[3] = {1, 2, 3};
for (int i = 0; i <= 3; ++i)     // 注意是 <= 3，越界了
    std::cout << a[i] << " ";
```

- `g++ -std=c++17 -Wall -Wextra` 编译：**零警告，生成 exe 成功**
- 运行结果：输出 `1 2 3 3`，**退出码 0（正常结束！）**
- 那个多出来的 `3` 是**内存里的垃圾数据**，这次恰好是 3，下次可能是一千万，也可能是负数
- 结论：**编译通过 + 没崩溃 + 退出码 0，程序依然是错的**

> 所以真正能救你的是**测试**——把边界情况都试一遍（比如数组的 `i = size`、字符串的首尾字符、除数为 0、空容器）。

**原始作答记录**

> 数组越界访问

**核对结果**

- ✅ 对。这个例子选得准，属于「编译通过但程序错了」的典型案例。
- 只是太简略：题目要求「说明为什么」+「举一个例子」，答案只给了例子。

> **订正说明（补充而非改错）**：原答案写的是「数组越界访问」，例子正确；补充说明应为「因为编译器只检查**语法和类型**，检查不了**运行时才确定的值和逻辑**——数组越界属于**未定义行为**，编译器默认不检查数组下标，所以它**连警告都不给**，还能正常生成 exe」，因为「编译通过≠程序对」的**原因**在于编译器看不到运行时才确定的值，这一点原答案没有点出来。

## 任务 5 · 找 bug 练习：凯撒密码在 `XYZ` 上输出 `[\]`

### 第一问：根本原因是什么？

**参考答案**

```cpp
s[i] = 'A' + (s[i] - 'A' + 3);
```

逐步算一遍输入 `'X'` 的情况：

| 表达式 | 值 | 说明 |
|---|---|---|
| `'X' - 'A'` | `23` | `'X'` 是第 24 个字母，偏移量是 23（A 是 0） |
| `'X' - 'A' + 3` | `26` | **越过了 `'Z'`（偏移量 25），跑到字母表外面去了** |
| `'A' + 26` | `'['` | ASCII 码里 `'Z'` 是 90，`'A' + 26` = 91 = `'['` |
| 同理 `'Y'` → `'\'`，`'Z'` → `']'` | | 所以输出 `[\]` |

**根本原因：偏移量累加后超过了 25，却没有「绕回」字母表开头。**

**修复方法：对 26 取模。**

```cpp
s[i] = 'A' + (s[i] - 'A' + 3) % 26;    // 26 是字母个数
```

取模以后：`(23 + 3) % 26 = 0` → `'A' + 0 = 'A'`；`'Y'` → `'B'`；`'Z'` → `'C'`。输出正确变成 `ABC`。

**这类错误的学名：边界条件 bug（off-by-one / wrap-around bug）** ——只测了 `abc` 这种「顺利的中间情况」，没有测 `XYZ` 这种「顶到边界的情况」。

**原始作答记录**

> 因为这些字母用 ascll 码表示，ascll 码同时也有代指一些特殊字符的编号，并且 ascll 码的码是顺序的，所以就会出现这种情况

**核对结果**

- 「字母用 ASCII 码表示」「ASCII 码也用来表示特殊字符」「ASCII 码是连续的 / 有序的」——✅ 这三句本身都对，是理解这个 bug 的**必要背景**。
- 但**没有指出根本原因**（偏移量超 25 没取模、没有绕回）。

> **订正说明**：原答案写的是「因为这些字母用 ASCII 码表示，ASCII 码同时也有代指一些特殊字符的编号，并且 ASCII 码的码是顺序的」——这些话描述的是**现象的背景**，正确应为「根本原因是**偏移量超过 25 之后没有绕回字母表开头**：`'X' - 'A' + 3 = 26 > 25`，`'A' + 26` 就落到了 `'Z'` 后面的字符 `'['` 上，修复办法是**对 26 取模** `% 26`」，因为题目问的是「**根本原因**」，答「用了 ASCII 码」等于没答——ASCII 连续性恰恰是这个算法**成立的前提**，出问题的是**忘了处理溢出边界**。

### 第二问：这个 bug 属于哪一类错误？（编译 / 链接 / 运行时）

**参考答案**

**运行时错误**（更准确地说：**运行时才发作的逻辑错误 / 未定义行为**）。

- 语法和类型完全合法，**编译 0 报错、0 警告，链接也正常，exe 正常生成**。
- 只有**运行起来、且输入恰好踩到边界（`XYZ`）**时，结果才是错的。
- 而且它**不会崩溃**：照常打印 `[\]`，退出码 0。这正是它危险的地方——和错误分类实验 E 属于同一类。

**原始作答记录**

> 我觉得是运行时

**核对结果**

- ✅ **完全正确。**

> 无需订正。（原答案用了「我觉得」，说明是推理出来的而不是背的，这个方向是对的。）

### 第三问：为什么只看"输入 `abc` 输出 `def`"发现不了它？你会多测哪几个输入？

**参考答案**

**为什么发现不了**：`abc` 里的每个字母偏移 3 位后都**没有越过 `Z`**，走的全是「顺利路径」。测试用例只覆盖了中间情况，**没覆盖边界**，所以 bug 藏在了没被走到的代码分支里。

> 这是新手最常见的失分点：**用「典型输入」测通了，就以为程序对了。**
> 程序在边界上的行为，和它在中间的行为，是两件事。

**应该多测哪些输入**：

| 测什么 | 具体输入 | 会暴露什么 |
|---|---|---|
| **字母表末尾边界** | `XYZ` → 应为 `ABC` | 直接命中本题的 bug |
| **字母表开头** | `ABC` → 应为 `DEF` | 确认起点偏移正确 |
| **单个字母的边界** | `Z`、`z` | 最极端的越界情况 |
| **大小写混合** | `aBcXyZ` | 小写 `'a' + 26` 会跑到 `'{'`，同样的问题 |
| **非字母字符** | `a1!Z` | 数字和符号应原样保留，不该被偏移 |
| **空字符串** | `""` | 循环体一次都不该执行 |
| **正好绕一圈** | 偏移 26 位（等价于 0 位） | 结果应等于原文 |

一句话原则：**测「第一个」「最后一个」「空的」「刚好越界的」，别只测中间的。**
