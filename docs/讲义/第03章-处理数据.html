第 0 部分 · 零基础补白：类型到底是什么

这一部分（第 1–3 节）是给零基础读者的地基。 如果你已经知道"什么叫数据类型""二进制怎么算""为什么有有符号和无符号"， 可以跳过，直接从 第 4 节 开始。

1. 先把「数据」和「变量」讲清楚

1.1 程序在干什么？

一个程序本质上只在做一件事：把数据搬进内存、算一算、再搬出来。

int age = 18;              // 把 18 存进内存
age = age + 1;             // 把内存里的数取出来，加 1，再存回去
std::cout << age;          // 把内存里的数送到屏幕上
  • 内存（memory）：一长排极小的"格子"，每个格子只能存 0 或 1。这是硬件决定的——一个开关要么开（1）要么关（0）。
  • 变量（variable）：你给某个格子起的名字。age 只是一个标签，真正存东西的是内存。
  • 数据类型（data type）：告诉编译器"这个格子里的 0/1 该怎么解释"。

1.2 什么是数据类型？为什么计算机要区分类型？

数据类型的本质是一份"解读说明书 + 占用空间说明书"。

同一串 0 和 1，用不同的"说明书"去读，得到的东西完全不同：

内存里的一串 0/1：  0100 0001
  按 char  读  →  字符 'A'
  按 int   读  →  数字 65
  按别的规则读 →  可能是别的东西

类型至少决定了三件事：

类型告诉我什么 例子
占多少空间 short 占 2 字节，int 占 4 字节
怎么解读这些位 整数按二进制数数；小数按"符号 + 指数 + 尾数"解读
能做哪些运算 整数能 % 取余；小数不能（见第 9.4 节）

为什么非要区分？ 因为内存有限，而不同的用途要"够用的范围"和"省内存"之间取舍：

  • 你要存一个班级的人数（0–100），用 1 字节就够，没必要花 8 字节；
  • 你要存全世界的人口（约 80 亿），1 字节最大只能到 255，根本装不下，必须用 8 字节的 long long。

类比：整数像用格子数数，小数像科学计数法。

  • 整数就像抽屉里的格子：一格一个，格子数是固定的。short 有 65536 个格子，能表示 -32768 到 32767，多一个都放不进去（放进去就"溢出"，见 4.3）。
  • 小数（浮点数）像科学计数法 3.14 × 10²：用"有效数字 + 指数"两部分来记。 好处是能表示极大极小的数（1.5e300、1.5e-300），坏处是有效数字位数有限—— 超出位数就只能四舍五入，于是有了精度误差（见第 7 节）。

2. 计算机怎么存整数：二进制基础（教材附录 A，p856–858；对应 3.1.3 p56）

这一节是整章的地基。跳过它，后面"为什么 short 最大是 32767"就只能死记硬背。

2.1 十进制：我们习惯的"数位"

十进制的规则是"每一位是 10 的几次幂"：

2468 = 2×1000 + 4×100 + 6×10 + 8×1
     = 2×10³  + 4×10² + 6×10¹ + 8×10⁰

注意两个约定（教材 p856 特意提醒）：

  • 任何非零数的 0 次幂都是 1，所以 10⁰ = 1；
  • 基数是几，就用 0 到几-1 这几个数字。十进制基数 10，所以用 0–9。

2.2 二进制：计算机真正用的数位

计算机的每个存储单元只有"开 / 关"两种状态，所以它天然用基数 2，只用两个数字：0 和 1。

二进制   10011011
       = 1×2⁷ + 0×2⁶ + 0×2⁵ + 1×2⁴ + 1×2³ + 0×2² + 1×2¹ + 1×2⁰
       = 128  + 0    + 0    + 16   + 8    + 0    + 2    + 1
       = 155

（这是教材 p858 的原例。）

每一位对应的"权重"背下来会非常有用：

位编号 7 6 5 4 3 2 1 0
权重（2 的幂） 128 64 32 16 8 4 2 1

1 字节（byte）= 8 位（bit），所以 1 字节能表示 2⁸ = 256 个不同的组合，也就是 0 ~ 255。

⚠️ 注意教材的严谨说法（p858）：C++ 的"字节"并非一定是 8 位，但附录采用常见做法，用"字节"表示 8 位组。本书（以及绝大多数 PC 平台）都是 1 字节 = 8 位。

8 位全 1 是多少？ 把 8 个权重全部加起来：

128 + 64 + 32 + 16 + 8 + 4 + 2 + 1 = 255

这就是为什么无符号 1 字节最大是 255。

2.3 为什么 short 最大正好是 32767？

short 占 2 字节 = 16 位。16 位全 1 的话：

2¹⁶ - 1 = 65535

但 short 是有符号的，最高位被拿去当符号位了（见第 3 节），只剩 15 位放数值：

2¹⁵ - 1 = 32768 - 1 = 32767        ← short 的最大值
-2¹⁵    = -32768                   ← short 的最小值

跑一遍 示例代码/03_xxx/01_limits_and_overflow.cpp，你会看到这张表（在这本书的 Windows/MinGW64 环境下实测）：

类型            字节   取值范围
short           2      -32768 ~ 32767
int             4      -2147483648 ~ 2147483647
long            4      -2147483648 ~ 2147483647
long long       8      -9223372036854775808 ~ 9223372036854775807
unsigned int    4      0 ~ 4294967295

对照一下规律，全都能用"2 的幂减 1"推出来：

类型 字节 位数 最大值 计算式
short 2 16（15 位数值 + 1 位符号） 32767 2¹⁵ - 1
int 4 32（31 + 1） 2147483647 2³¹ - 1
long long 8 64（63 + 1） 9223372036854775807 2⁶³ - 1
unsigned int 4 32（全部 32 位都放数值） 4294967295 2³² - 1

看到 2³¹ - 1 = 2147483647 这个数，你就知道 int 的边界从哪来了。

⚠️ 注意 long 那一行：在 Windows/MinGW 上 long 也是 4 字节，和 int 一样！ 教材（p57）说"long 至少 32 位"——"至少"两个字就是关键，具体多长由实现决定。 在 Linux 上 long 是 8 字节。同一个程序在两个平台上行为不同，这就是可移植性问题 （第 1 章「预备知识」讲过）。 实践建议：需要大整数就用 long long，别用 long。

2.4 顺便：C++ 还支持八进制和十六进制字面值

教材把附录 A 放在全书最后，但它的前两节（八进制 / 十六进制）在这一章就会用到。

进制 基数 允许的数字 C++ 的写法 例子 十进制值
十进制 10 0–9 什么都不加 42 42
八进制 8 0–7 前缀 0 042 34
十六进制 16 0–9、a–f 前缀 0x 或 0X 0x2A 42
二进制 2 0、1 C++ 没有二进制字面值（教材 p858 明确说了） — —

十六进制里 a–f 分别表示 10–15（教材表 A.1，p858）：

十六进制数 十进制值
a 或 A 10
b 或 B 11
c 或 C 12
d 或 D 13
e 或 E 14
f 或 F 15

记忆法：十六进制的 1 位 = 二进制的 4 位（因为 2⁴ = 16），所以十六进制是给人看二进制的"压缩写法"。硬件文档里（内存地址、端口号）几乎全用十六进制。

最容易踩的坑：042 不是 42！前面的 0 是八进制标记。

int a = 42;
int b = 042;
std::cout << 42 << " " << 042 << " " << 0x2A << "\n";
// 实测输出：42 34 42        ← 042 是八进制，等于十进制的 34

✅ 这是 C++ 里一个非常隐蔽的 bug 来源。int day = 09; 甚至会编译报错，因为八进制里没有数字 9。

3. 为什么有"有符号"和"无符号"？最高位当符号位是什么意思

3.1 只有 16 个格子，怎么表示负数？

一组二进制位本身没有正负概念。为了让 short 能表示负数，C++（以及几乎所有现代计算机）采用的做法是：

把最高位（最左边那一位）单独拿出来当"符号位"：0 表示正，1 表示负。

于是 16 位被切成两半：

short（16 位）：
  位 15        位 14 ... 位 0
  ┌───┐  ┌──────────────────┐
  │符号│  │   15 位数值部分   │
  └───┘  └──────────────────┘
   0 → 非负         1 → 负数
  • 有符号（signed）：最高位当符号位 → 数值部分只剩 15 位 → 范围 -32768 ~ 32767。 正数和负数的"格子"是共享的：一半给正，一半给负。
  • 无符号（unsigned）：最高位也拿来放数值 → 16 位全用 → 范围 0 ~ 65535。 代价是不能表示负数。

一句话总结：unsigned 并没有"多出格子"，只是把负数那一半的格子挪用给了正数。 所以 unsigned short 的最大值是 signed short 最大值的两倍多一点（32767 → 65535）。

3.2 有符号整数的范围为什么是不对称的？

你会发现：short 是 -32768 ~ 32767，负数比正数多一个。原因在于全 0 也被算在正数那一半：

符号位 数值位 表示
0 全 0 0
0 最大 +32767
1 全 0 −32768（不是 −0）
1 最大 −1

16 位一共 2¹⁶ = 65536 个组合，平均分给正负两半是 32768。正的那一半里有一个组合被 0 占了，所以正数只有 32767 个，而负数那一半 32768 个全用得上。

📌 现代计算机实际用的是补码（two's complement）表示负数，上面这张表就是补码的效果。 你不需要会算补码，但要记住这个结论：short 的范围是 -32768 ~ 32767，不对称。

3.3 用代码亲眼看一下

#include <iostream>
#include <climits>
int main()
{
    std::cout << "short 最大: " << SHRT_MAX << "\n";        // 32767
    std::cout << "short 最小: " << SHRT_MIN << "\n";        // -32768
    std::cout << "int   最大: " << INT_MAX << "\n";         // 2147483647
    std::cout << "unsigned int 最大: " << UINT_MAX << "\n"; // 4294967295
}

（<climits> 头文件里定义了 SHRT_MAX、INT_MAX、UINT_MAX 这些常量，见 示例代码/03_xxx/01_limits_and_overflow.cpp。）

4. 为什么有这么多整型（3.1.2–3.1.5，p56–62）

上一节解释了"有多大"，这一节回答"为什么要分这么细"。

答案：为了在"够用的范围"和"省内存"之间取舍。

一个实际的例子：

场景 需要的范围 该用什么 如果选错了
一个班的编号 0–100 short 甚至 unsigned char 用 long long 只是浪费内存
全国人口 约 14 亿 int（上限 21.4 亿）刚好 用 short 直接溢出
世界人口 约 80 亿 必须 long long 用 int 溢出成负数

选类型的口诀：预估数据的最大范围，然后取两倍以上的余量。

4.2 溢出：C++ 不救你（教材复习题第 3 题）

跑一遍 示例代码/03_xxx/01_limits_and_overflow.cpp：

short 最大值      : 32767
加 1 之后         : -32768      ← 翻到负数去了
unsigned short 0-1: 65535       ← 绕回最大值

教材复习题第 3 题问的就是这个："C++ 提供了什么措施来防止超出整型的范围？"

答案：几乎什么都没提供。 C++ 不会在运行时检查溢出，不加任何保护——因为检查要花时间，而 C++ 的设计哲学是"不为你不需要的东西付费"。

后果有多严重？

int a = 2147483647;
int b = a + 1;              // 不报错、不崩溃，b 变成 -2147483648

如果你的程序在算钱，这一刻就出事了。

为什么加 1 会变成负数？ 因为 2147483647 的 32 位是 0111...1（最高位 0）。加 1 之后进位把最高位变成了 1，于是被当成负数读——这就是"翻转"（wrap around）。

唯一能做的：

  1. 选对类型（预估数据范围，取两倍余量）
  2. 需要更大就用 long long
  3. 现实中要精确大数，得用专门的大数库（不在标准库里）

4.3 怎么提前发现溢出风险？

信号 说明
数据类型上限接近你的数据量 例如用 int 存 40 亿，上限 21.4 亿 → 一定溢出
中间结果会很大 a * b 即使最终结果小，中间结果也可能溢出
死循环 / 结果突然变负 典型溢出症状

中间结果溢出是个容易忽略的坑（数据是实测的）：

int a = 100000, b = 100000;
int c = a * b / 100000;                    // ❌ 实测得到 14100，正确值是 100000
long long d = (long long)a * b / 100000;   // ✅ 先转成 long long 再乘，得到 100000

为什么 c 是 14100？ 因为 a * b 这一步先在 int 里算：精确值 100 亿（10¹⁰）远超 int 上限 21.4 亿，于是发生了翻转，得到一个莫名其妙的值，后面再除就全错了。 注意：最终结果 100000 明明很小，但中间结果超了——这类 bug 最难看出来。

一个必须知道的补充说明：有符号整数的溢出在 C++ 标准里叫未定义行为（undefined behavior）， 意思是"标准不保证发生什么"。实测在这台机器上（MinGW64，不加优化）表现为"按 32 位翻转"， 但同一段代码加上 -O2 优化后可能表现完全不同。所以：

  • 不要指望"溢出会稳定地翻转"；
  • 更不要写依赖溢出结果的代码；
  • 唯一的办法是提前选对类型。

（对比一下：无符号整数的溢出是有定义的，标准明确规定"按 2ⁿ 取模"， 这就是 5u - 10u 能得到 4294967291 的原因。）

4.4 unsigned 的陷阱（3.1.4，p60）

unsigned 表示"只有非负数"，范围变成 0 ~ 2×正数上限。听起来很好？它有反直觉的坑：

unsigned int u = 5;
unsigned int v = 10;
if (u - v > 0)        // ← 你以为 5-10 = -5，所以不成立？
    cout << "居然进来了！";   // ← 这行会执行！

因为 5 - 10 在无符号世界里不是 -5，而是绕回来的一个巨大正数：

实测：5u - 10u = 4294967291       ← 不是 -5！

为什么？ 无符号数的减法在数学上是"模 2³²"的运算：5 - 10 + 2³² = 4294967291。 既然它是个正数，> 0 就成立了。

⚠️ 给零基础读者的建议：学习阶段尽量别用 unsigned。教材 p62 也说了， 只在"确实需要多一位正数范围"或"做位运算"时才用。日常用 int 就好。

另外注意：unsigned 和 int 混在一个表达式里时，int 会被提升成 unsigned， 于是负数字面值会产生更离奇的结果。这也是"别用 unsigned"的理由之一。

4.5 sizeof：问编译器"它有多大"

std::cout << sizeof(short) << "\n";       // 2
std::cout << sizeof(long double) << "\n"; // 16（MinGW64）
  • sizeof 的单位是字节，不是位。
  • sizeof 的结果类型是 size_t（无符号整型）。

5. char 的真面目：它就是个很小的整数（3.1.8，p64–70）

5.1 char 存的是数字，不是"字符"

计算机里没有"字母"这种东西，只有数字。所谓的字符，是约定了一张对照表： 数字 65 代表 A，数字 66 代表 B……这张表叫 ASCII（教材附录 C，p862）。

所以 char 本质上就是一个 1 字节的整数，只是被约定用来存编码。

跑 示例代码/03_xxx/03_char_is_number.cpp：

char grade1 = 65;  输出: A
char grade2 = 'A'; 输出: A
把它们的数值打出来: 65 和 65
-> 等价！因为 'A' 的 ASCII 编码就是 65

教材复习题第 5 题就是在问这个（char grade = 65; 和 char grade = 'A'; 等价吗？等价）。

为什么 I/O 系统知道该显示 A 还是 65？

cout << c       -> A        (当字符)
cout << (int)c  -> 65       (当数字)

同一块 8 bit 的内存，解释方式不同，显示就不同。 这就是教材 p70 那句话的意思。

第 6 题（找出编码 88 表示的字符）两种方法：

cout << (char)88;                 // 强制转换
char c = 88;  cout << c;         // 用 char 变量
// 都输出 X（ASCII 88 = 'X'）

这一节真正的价值：理解了 'A' 就是 65，你才能理解凯撒密码类的 bug—— 'X' + 3 会跑到 '[' 去，因为 'X'(88) + 3 = 91 = '['。字符运算就是整数运算。

5.4 bool 类型（3.1.9，p70–71）

bool 只有两个值：true 和 false。

bool flag = true;

关键事实：

  • bool 的 sizeof 是 1 字节（实测）。
  • true 在算术里等于 1，false 等于 0，所以 true + true 是 2。

🔍 反直觉点：-1 是 true。所以 while (n) 这种写法在 n 为负数时也会继续循环。

6. const：给常量起个名字（3.2，p71）

6.1 为什么不能直接写数字？

double inches = feet * 12;        // 12 是什么？
double meters = inches * 0.0254;  // 0.0254 又是什么？

半年后回来看这段代码，你会问自己"12 是英尺换算还是铅笔数量？"。 把魔法数字（magic number）换成有名字的常量，代码立刻能读懂。

const int kFeetPerYard = 3;           // 之后不能再改
const double kInchToMeter = 0.0254;   // 学习阶段建议常量加 k 前缀

6.2 const 和 #define 的区别

#define 是 C 语言的老写法，也能定义常量：

#define INCH_TO_METER 0.0254      // 老写法
const double kInchToMeter = 0.0254;  // ✅ 推荐

教材 p71 的核心一句话（大意）：const 比 #define 好，因为 ① 它能指定类型 ② 它遵循作用域规则 ③ 编译器能对它做类型检查。

展开讲为什么：

对比项 const double X = 0.0254; #define X 0.0254
有类型吗 ✅ 有，就是 double ❌ 没有类型，它只是文本
编译器做类型检查吗 ✅ 会 ❌ 不会
有作用域吗 ✅ 有（可以定义在函数/类里） ❌ 没有，从定义处到文件末尾全都生效
出错的提示 会说"double 和 int 类型不匹配" 会说"某行有一堆括号展开失败"，看不懂
调试器里能看吗 ✅ 能 ❌ 看不到
遵守命名空间吗 ✅ 遵守 ❌ 不遵守
本质是什么 一个真正的变量，只是不能改 预处理阶段的文本替换

#define 为什么容易出 bug？ 因为它是纯文本替换，不认优先级：

#define DOUBLE_X 2 * 3
int a = DOUBLE_X * 4;    // 展开成 2 * 3 * 4 = 24（这次对）
#define DOUBLE_Y (2 + 3)
int b = DOUBLE_Y * 4;    // ✅ 有括号才对
#define BAD (2 + 3)
int c = BAD * 4;         // 用 BAD 的人不知道有括号，还好这里写了

再比如：

#define SQUARE(x) x * x
SQUARE(1 + 2)      // 展开成 1 + 2 * 1 + 2 = 5，不是 9！

这种错误 const 根本不会犯，因为 const 是先算好值，再做类型检查。

用 const 的额外好处：名字出现在编译器的符号表里，所以：

  • 编译器能提醒你"kInchToMeter 写错了"（拼错 #define 的名字只会报"未定义标识符"，指向不着边际的位置）；
  • 调试时能看到它的值；
  • 把 #define 换成 const，还能少一个宏污染全局命名空间的机会。

6.3 const 的几条规则

const int a = 10;
a = 20;                  // ❌ 编译错误：attempting to assign to a const

const int b;             // ❌ 编译错误：const 变量必须初始化
const int c = 10;        // ✅ 正确

必须初始化的理由：定义之后就不能再赋值了，如果定义时也不给值，那它就永远没有值。

这一课你就要用上它：编程练习里明确要求"用符号常量表示转换因子"。

const double kInchToMeter = 0.0254;   // 学习阶段建议常量加 k 前缀
const int kSecPerDay = 24 * 60 * 60;  // 编译器会在编译期算好这个值

📌 const 是 C++ 里最重要的关键字之一。后面会见到它的各种变体： const int*、int* const、const 成员函数、const 引用……（第 7、8、10 章）

7. 计算机怎么存小数：浮点数与精度（3.3，p72–75）

7.1 核心思想：像科学计数法一样存

本小节的目的只是让你明白为什么会有精度误差，不需要会手动转换，知道"IEEE 754"这个名字就行。

先看整数为什么不够用。 整数用"格子数数"，格子的间隔永远是 1：

short 能表示：... -2  -1   0   1   2  ...  32767     ← 全是整数，没有中间值
  • 表示不了 3.14；
  • 稍微大一点就溢出。

小数的需求：既要能表示 3.14，又要能表示 1.5e300（比整数范围大得多）。 于是计算机改用科学计数法的思路：

十进制科学计数法：  3.14 × 10²      = 3.14 × 100
二进制浮点数：      1.011 × 2⁵      （有效数字 × 2 的幂）

一个存储单元被切成三部分：

┌──────┬────────────┬──────────────────────┐
│ 符号 │   指数部分   │      尾数（有效数字） │
│ 1 位 │   8 位      │        23 位          │   ← float（共 32 位）
└──────┴────────────┴──────────────────────┘

┌──────┬────────────┬──────────────────────┐
│ 符号 │  11 位指数   │      52 位尾数        │   ← double（共 64 位）
└──────┴────────────┴──────────────────────┘
  • 符号位：正还是负；
  • 指数部分：小数点往哪挪（决定"量级"，能表示极大极小）；
  • 尾数部分：有效数字的位数（决定精度）。

这套二进制浮点格式的国际标准叫 IEEE 754，上面这张位布局就是它的规定。

关键结论：double 的尾数有 52 位（加上隐含的 1 位，有效位约 53 位二进制）→ 换算成十进制大约 15–16 位有效数字，这就是"double 有约 15–16 位有效数字"的来源。 float 的尾数是 23 位 → 约 6–7 位有效数字。

7.2 ⭐ 精度陷阱（教材复习题第 7 题）

跑 示例代码/03_xxx/04_float_precision.cpp，看这个经典：

double 0.1 + 0.2 = 0.3
d == 0.3 的结果是: false！
用 17 位精度看: 0.30000000000000004

原因：0.1 在二进制里是无限循环小数（就像 1/3 在十进制里是 0.3333...）， double 只有 64 位，存不下，只能近似。

一步步看清楚：

① 十进制小数怎么变成二进制？ 反复"乘 2，看是否 ≥ 1"：

0.625 × 2 = 1.25   → 取 1，余 0.25
0.25  × 2 = 0.5    → 取 0，余 0.5
0.5   × 2 = 1.0    → 取 1，余 0
→ 0.625 的二进制是 0.101，除尽了，所以能精确存储 ✅

② 同样的办法算 0.1：

0.1 × 2 = 0.2  → 0
0.2 × 2 = 0.4  → 0
0.4 × 2 = 0.8  → 0
0.8 × 2 = 1.6  → 1，余 0.6
0.6 × 2 = 1.2  → 1，余 0.2      ← 又回到 0.2！开始循环
...        → 永远除不尽
→ 0.1 的二进制是 0.000110011001100110011... 无限循环 ❌

③ 计算机只好截断。 double 里存的 0.1，真实值是：

0.1000000000000000055511151231257827021181583404541015625

它比 0.1 略大一点点。两个这样的近似值相加，误差就露出来了：

0.1 + 0.2 = 0.30000000000000004   （而不是 0.3）

一句话：浮点数只能表示"分母是 2 的幂"的小数，0.1、0.2、0.3 都不是。

⚠️ 铁律：浮点数永远不要用 == 比较！ ```cpp // ❌ 错 if (a == b) ...

// ✅ 对：判断差值足够小

include

if (fabs(a - b) < 1e-9) ... ```

1e-9 就是 1 × 10⁻⁹（科学计数法写法，见 7.5）。这个"允许的误差"通常叫 epsilon。

比较式的选择：

场景 推荐写法
比较是否相等 fabs(a - b) < 1e-9
比较大小 a < b - 1e-9（避免"差一点点"误判）
判断是否为 0 fabs(a) < 1e-9

那什么时候可以放心用 ==？ 比较同一个变量、比较整数赋给浮点数的值、比较 0.5、0.25 这类分母是 2 的幂的数——它们能精确存储。但养成习惯用差值判断更安全。

7.3 三种浮点类型

类型 字节（MinGW64） 有效数字 什么时候用
float 4 约 6–7 位 省内存、图形学
double 8 约 15–16 位 默认就用它
long double 16 更多 特殊计算

记一条：默认用 double。写 3.14 是 double，写 3.14f 才是 float。

教材复习题第 7 题（long → float / double 会不会有舍入误差）实测：

long   = 123456789
float  = 123456792   <- 有误差！
double = 123456789   <- 通常没问题

float 只有约 7 位有效数字，而 123456789 有 9 位 → 装不下 → 后两位被改了。

long long 赋给 double 呢？ long long 有 64 位，而 double 的有效位约 53 位 → 超过约 9×10¹⁵ 的整数会开始丢精度。所以"double 完全安全"只对 long（32 位）成立。

一个亲手可验的例子（float 的有效数字边界）：

float f = 16777216.0f;     // 2²⁴
std::cout << f + 1.0f;     // 实测输出 16777216 —— 加 1 加不上去！

因为 float 的尾数放不下 2²⁴+1 的精度，这个 1 被直接丢掉了。

7.4 不要用浮点数做"精确"计算

场景 该用什么
算钱（分、角） 整数（用"分"为单位）
大数精确运算 专门的大数库（不在标准库里）
科学计算、图形 double（有误差但可接受）

算钱为什么不能用 double？ 因为累加 100 万次 0.01 会累积误差，最后对不上账。

7.5 浮点常量与科学计数法（3.3.1，p72）

3.14          // double
3.14f         // float
3.14L         // long double
3.14e2        // 3.14 × 10² = 314        （e 表示"10 的几次方"）
3.14e-2       // 3.14 × 10⁻² = 0.0314
3.14E2        // 大写 E 也行
.5            // 允许省略整数部分（不好看，别这么写）
5.            // 允许省略小数部分（危险：5. 是 double，5 是 int）

1e-9 就是"1 乘 10 的 -9 次方"，也就是 0.000000001。看到 e 就念成"×10 的几次方"。

7.6 控制输出精度（这是编程练习要用的）

浮点数默认按"6 位有效数字"打印出来，所以要控制显示的时候得用 <iomanip>：

#include <iomanip>
cout << fixed << setprecision(4) << value;   // 固定 4 位小数

两个开关要分清：

写法 含义 输入 37.855277 输出
setprecision(4) 4 位有效数字（默认模式） 37.855277 37.86
fixed << setprecision(4) 小数点后 4 位 37.855277 37.8553
setprecision(6) 6 位有效数字 37.855277 37.8553
setprecision(17) 17 位有效数字（看真相用） 0.1+0.2 0.30000000000000004

⚠️ fixed 一旦打开就一直有效，后面的输出全都受影响。要恢复默认得写 cout.unsetf(ios::fixed);。这是新手很容易被坑的地方。

教材 p87 练习 3 要求输出 37.8553，就是这么控制的：

37 + 51/60 + 19/3600 = 37.85527777...
保留 4 位小数 → 37.8553

注意 51/60 的陷阱：如果两个都是 int，51/60 会得到 0！必须写 51.0/60 或把变量声明为 double（详见第 9 节）。

8. 运算符的优先级和结合性（3.4.1，p77）

8.1 什么是优先级？

看这个表达式：

1 + 2 * 3

结果是 7，不是 9。因为乘法比加法先算——这就是优先级（precedence）。

1 + 2 * 3
    └─┬─┘        ① 先算乘法：2*3 = 6
1 +   6
└──┬──┘          ② 再算加法：1+6 = 7
   7

优先级就是从小学的那套"先乘除、后加减"，C++ 和数学基本一致。

想改变顺序就用括号——括号的优先级最高：

(1 + 2) * 3      // = 9

8.2 什么是结合性？

优先级只解决"不同运算符之间谁先算"。同一优先级的运算符接着算谁？靠结合性（associativity）：

10 - 4 - 3

减法从左到右结合（左结合）：

(10 - 4) - 3 = 6 - 3 = 3       ← 实际结果
10 - (4 - 3) = 10 - 1 = 9      ← 不是这个！

乘、除、求模也都是左结合——这一点下面第 9 节会变成一个真正的坑：

100 / 10 / 2     = (100/10)/2 = 5      ← 左结合
100 / (10/2)     = 100/5     = 20      ← 加了括号就完全不同

8.3 优先级速查表（够用版）

从高到低：

级别 运算符 结合性 例子
1（最高） () 括号 — (1+2)*3 = 9
2 一元 + - ! 右结合 -2 * -3 = 6
3 * / % 左结合 6*3/4 = 4
4 + -（二元） 左结合 2+3*4-5 = 9
5 << >>（流插入） 左结合 cout << a << b
6 < <= > >= 左结合 a < b
7 == != 左结合 a == b
8 && 左结合 a && b
9 \|\| 左结合 a \|\| b
10 = 赋值 右结合 a = b = c

几个必须记住的结论：

  1. * / % 三者优先级相同，都是左结合——这是第 9 节所有坑的来源。
  2. + - 比 * / % 低。
  3. 赋值 = 是右结合，所以 a = b = 0 等价于 a = (b = 0)。
  4. << 的优先级比你想象的低，所以 cout << a + b 会先算 a + b（这正是我们想要的）， 但 cout << a ? "x" : "y" 会出问题（需要加括号）。

8.4 实用的三条建议

  1. 不确定就加括号。 括号不花钱，而且让读代码的人不用去查表。
  2. 别写又长又复杂的表达式，拆成几行更清楚。
  3. cout << a << b 是链式调用，从左到右，所以输出顺序就是书写顺序。

更完整的优先级表见教材附录 D（p866）。

9. ⭐⭐ 整数除法与求模（3.4.2–3.4.3，p77–78）—— 本课第一大坑

这是本章最重要的一节。

9.1 整数除法：小数直接丢掉

跑 示例代码/03_xxx/02_division_and_modulo.cpp：

7 / 2   = 3        <- 不是 3.5，也不是四舍五入的 4
-7 / 2  = -3       <- C++11 起：向 0 截断

规则：两个整数相除，结果还是整数，小数部分直接砍掉（不是四舍五入）。

为什么？ 因为两个 int 相除，编译器按"整数运算"处理，结果也必须是 int。 3.5 没法放进一个只能存整数的格子里，所以小数部分被丢弃。

"向 0 截断"是什么意思？

表达式 数学结果 C++ 结果 说明
7 / 2 3.5 3 向 0 方向砍
-7 / 2 -3.5 -3 向 0 方向砍（不是 -4）
7 / -2 -3.5 -3 同上

C++11 之前，-7/2 是 -3 还是 -4 由编译器决定；C++11 起明确规定向 0 截断。 这是可移植性的一个真实例子。

想得到小数怎么办？只要让至少一个操作数是浮点：

7 / 2        // 3        ❌
7.0 / 2      // 3.5      ✅
7 / 2.0      // 3.5      ✅
(double)7/2  // 3.5      ✅

9.2 ⭐ 复习题第 8 题：6*3/4 和 3/4*6 为什么不一样？

b. 6 * 3 / 4   = 4      <- 先算 6*3 = 18，再 18/4 = 4
c. 3 / 4 * 6   = 0      <- 先算 3/4 = 0，再 0*6 = 0

两个表达式数字完全一样、运算符完全一样，结果却不同！

原因：* 和 / 优先级相同，按从左到右结合。所以中间结果不同：

  • b 的中间结果是 18（好）
  • c 的中间结果是 0（小数被砍掉了，后面再怎么乘都是 0）
6 * 3 / 4              3 / 4 * 6
└─┬─┘                  └─┬─┘
 18                      0            ← 3/4 的数学结果是 0.75，被砍成 0
 18 / 4 = 4             0 * 6 = 0

这就是那条规律：整数除法一旦把小数砍掉，后面再怎么补救都没用。

9.3 ⭐ 摄氏转华氏的经典写法

教材给的公式是 °F = 9/5 × °C + 32。很多人第一次写摄氏转华氏时会写成 9/5*c+32， 而这里藏着陷阱：

double c = 100;
9 / 5 * c + 32       // ❌ 实测 132，完全错了
9.0 / 5 * c + 32     // ✅ 实测 212
1.8 * c + 32         // ✅ 实测 212

为什么错得这么离谱？ 因为 9 / 5 先算：

9 / 5 * c + 32   →  1 * c + 32   →  c + 32     （100 + 32 = 132，错得离谱）
9.0 / 5 * c + 32 →  1.8 * c + 32 →  212        ✅

三条可选的写法：

写法 结果 评价
9 / 5 * c + 32 132 ❌ 整数除法陷阱
9.0 / 5 * c + 32 212 ✅ 正确，但每次都要算
1.8 * c + 32 212 ✅✅ 最好——能写常量就别留算式
(9.0 / 5) * c + 32 212 加括号更清楚

"能写常量就别留算式" 这条建议的理由：

  • 读者一眼看懂意图，不用心算；
  • 省掉一次运行时的除法（编译器虽然可能优化，但为什么不直接写清楚）；
  • 不会踩整数除法的坑——算式留在代码里，哪天有人改了类型就可能出事。

9.4 求模 %：取余数

15 % 4  = 3
15 % 5  = 0
-15 % 4 = -3      <- 余数的符号跟着**左边**走

两条规则：

  1. % 只能用于整数！15.0 % 4 会编译报错：

error: invalid operands of types 'double' and 'int' to binary 'operator%'

注意这是编译期错误（不是运行期），所以程序根本生成不出来。

  1. 结果的符号跟左操作数一致：
表达式 结果 说明
15 % 4 3 正 % 正 = 正
-15 % 4 -3 负 % 正 = 负（跟左边）
15 % -4 3 正 % 负 = 正（跟左边）

% 的三个典型用途：

if (n % 2 == 0) ...              // 判断奇偶
int lastDigit = n % 10;          // 取个位
int hours = totalMinutes / 60;   // 取商
int mins  = totalMinutes % 60;   // 取余   ← 这两个配对使用是固定套路

/ 和 % 是一对搭档，它们回答两个不同的问题：

totalMinutes = 135
totalMinutes / 60 = 2      ← 能装下几个 60？（商）
totalMinutes % 60 = 15     ← 装完之后还剩多少？（余数）
验证：2 * 60 + 15 = 135 ✅

这个"先除得商，再取模得余数"的模式，是本章所有练习的核心。

9.5 实战：秒数 → 天 / 时 / 分 / 秒

教材 p87 编程练习第 4 题（31600000 秒 → 天/时/分/秒）就是 / 和 % 的组合练习， 这道题必须做，它是本章的核心。

思路是一层一层往下剥：

总秒数 = 31600000

days    = 总秒数 / 86400      31600000 / 86400 = 365        （商 = 365 天）
剩下    = 总秒数 % 86400      31600000 % 86400 = 64000      （余数 = 64000 秒）
hours   = 剩下 / 3600         64000 / 3600 = 17             （商 = 17 小时）
剩下    = 剩下 % 3600         64000 % 3600 = 2800           （余数 = 2800 秒）
minutes = 剩下 / 60           2800 / 60 = 46                （商 = 46 分钟）
seconds = 剩下 % 60           2800 % 60 = 40                （余数 = 40 秒）

每一步都在问同样两个问题："能装下几个？"（用 /）"装完还剩多少？"（用 %）。 注意 % 拿到的是"剩下的秒数"，不是"剩下的小时数" —— 这是这题最容易算错的地方。 下面给出完整的验证代码。

验证方法（一定要自己验一遍）。两种验法：

验法一：把结果加回去。

365 × 86400 + 17 × 3600 + 46 × 60 + 40
= 31536000 + 61200 + 2760 + 40
= 31600000  ✅

验法二：检查中间值能不能"接上"。

365 天用掉          → 365 × 86400 = 31536000
还剩多少秒          → 31600000 - 31536000 = 64000      ← 和 % 的结果一致 ✅
64000 秒里有几小时   → 17 × 3600 = 61200
还剩多少秒          → 64000 - 61200 = 2800             ← 和第二个 % 的结果一致 ✅
2800 秒里有几分钟    → 46 × 60 = 2760
还剩多少秒          → 2800 - 2760 = 40                 ← 和最后一个 % 的结果一致 ✅

两种验法都指向同一组数字，这道题才算做对了。 （第二种验法更重要——它验证的是中间步骤，而不只是最终答案。 很多错误只有中间值才能暴露出来。）

完整可运行代码（已用 g++ -std=c++17 -Wall -Wextra 验证，含反向验证）：

#include <iostream>
int main()
{
    const long long kSecPerMin  = 60;
    const long long kSecPerHour = 60 * kSecPerMin;      // 3600
    const long long kSecPerDay  = 24 * kSecPerHour;     // 86400

    long long input = 31600000LL;
    long long total = input;

    long long days    = total / kSecPerDay;
    total = total % kSecPerDay;              // 扣掉整天，剩下的是"秒"
    long long hours   = total / kSecPerHour;
    total = total % kSecPerHour;             // 扣掉整小时，剩下的是"秒"
    long long minutes = total / kSecPerMin;
    long long seconds = total % kSecPerMin;

    std::cout << input << " seconds = " << days << " days, " << hours
              << " hours, " << minutes << " minutes, " << seconds << " seconds\n";

    // 反向验证：结果加回去应当等于输入
    long long back = days * kSecPerDay + hours * kSecPerHour
                   + minutes * kSecPerMin + seconds;
    std::cout << "反向验证: " << back << "  相等? " << (back == input) << "\n";
    return 0;
}

实测输出（第一行正是教材要求的格式）：

31600000 seconds = 365 days, 17 hours, 46 minutes, 40 seconds
反向验证: 31600000  相等? 1

用 const 定义 86400、3600、60，并且注意写成 24 * kSecPerHour 这种"用常量推常量" 的写法——它把换算关系写进了代码里，比硬编码 86400 更可读。

⚠️ 一个隐藏细节：把 60 * 60 * 24 写成 int 是安全的（86400 远小于 21 亿）。 但如果是"毫秒"这类更大的数字，int 就可能溢出，要提前用 long long。

/ 和 % 配对的另外两个例子：

// 英寸 → 英尺 + 英寸
int totalInches = 170;
int feet = totalInches / 12;      // 14
int inch = totalInches % 12;      // 2

// 分 -> 小时 + 分
int totalMin = 135;
int h = totalMin / 60;            // 2
int m = totalMin % 60;            // 15

9.6 除法的另一个坑：除以 0

int a = 5 / 0;         // ❌ 未定义行为（实际可能崩溃或产生垃圾值）
double b = 5.0 / 0.0;  // 浮点除 0 会得到 inf（无穷大），不是崩溃

整数除以 0 是未定义行为，程序可能崩溃、可能算出任何东西。写除法前先确认分母不为 0。

10. ⭐⭐ 类型转换（3.4.4，p79–83）—— 本课第二大坑

跑 示例代码/03_xxx/05_type_conversion.cpp。

10.1 隐式转换：编译器悄悄做的

int    i = 3.99;         // i = 3      ← 直接砍掉小数，不是四舍五入
double x = 7 / 2;        // x = 3.0    ← 右边先按整数算成 3！
double y = 7.0 / 2;      // y = 3.5    ← 有 double 参与才对

第一行最容易误解：很多人以为 int i = 3.99; 会四舍五入成 4。 不会。 把浮点转整数一律截断（向 0 砍）：

赋值 结果
int i = 3.99; 3
int i = 3.01; 3
int i = -3.99; -3（向 0 砍，不是 -4）

想要四舍五入，得自己写：

int rounded = (int)(x + 0.5);        // 正数可以这样
#include <cmath>
int r2 = (int)std::round(x);         // ✅ 标准做法

三条转换规则：

规则 说明
小类型 → 大类型 安全（char→int→long→double）
大类型 → 小类型 可能丢数据（double→int 丢小数；long→short 可能溢出）
表达式里只要有 double 整个表达式按 double 算

第 3 条最有用：7 / 2 是整数除法，但 7.0 / 2 是浮点除法—— 因为 2 被"提升"成 2.0 了。

为什么 double x = 7 / 2; 还是错的？ 因为赋值发生在最后一步：

7 / 2       →  先算右边的表达式，两个 int → 结果是 int 3
x = 3       →  再把 3 转成 double 3.0

转换的方向很重要：是从内往外算的，不是从外往内的。

10.2 转换发生的三个时机

时机 例子
赋值时 int i = 3.99;
运算中（类型提升） 7.0 / 2 里 2 提升为 2.0
传参 / 返回值时 函数要 double，你传 int

隐式转换的危险在于"静默"：编译器可能给个警告，但照样编译通过，程序跑起来结果就是错的。 这也是本章被称为"C++ 最多静默 bug 来源"的原因。

⚠️ 一个必须知道的事实（实测）：-Wall -Wextra 默认不会警告 double → int 的赋值丢精度。

int i = 3.99;      // g++ -Wall -Wextra：0 警告，编译通过

真想让它报警，得额外加 -Wconversion：

g++ -std=c++17 -Wall -Wextra -Wconversion 文件名.cpp -o 文件名

这时才会看到（实测原文）：

warning: conversion from 'double' to 'int' changes value
         from '3.9900000000000002e+0' to '3' [-Wfloat-conversion]
     int i = 3.99;
             ^~~~

结论：不要指望编译器替你抓类型转换问题。 -Wconversion 会带来很多噪音（正常的 int ↔ double 混合运算也会被报），所以日常不必强开， 但要知道"没警告"不等于"没问题"。

警告要认真看——它经常就是 bug 的提示。

10.3 显式转换（强制类型转换）

double pi = 3.14159;
(int)pi                    // C 风格 —— 能用，但不推荐
static_cast<int>(pi)       // C++ 风格 —— ✅ 推荐
int(pi)                    // 函数式 —— 也能用

三种写法效果完全一样，都是截断成 3。区别在"可读性 / 可搜索性"。

为什么推荐 static_cast？ 因为它能在代码里被搜出来。 类型转换是 bug 高发区，能搜到就能审查。C 风格的 (int) 混在一堆括号里根本找不出来：

foo(bar(x), (int)y);        // 你能一眼看出哪个是类型转换吗？
foo(bar(x), static_cast<int>(y));   // 一眼就能

（static_cast 是 C++ 四个转换运算符之一，第 15 章会讲另外三个： dynamic_cast、const_cast、reinterpret_cast。）

四者速览（现在只要知道名字）：

转换 用途
static_cast<T>(x) 一般转换，编译期可检查 ✅ 日常用这个
const_cast<T>(x) 去掉 const
reinterpret_cast<T>(x) 把内存按另一种类型重新解释（危险）
dynamic_cast<T>(x) 多态类型的安全下行转换

10.4 教材程序清单 3.14 的经典例子（p84）

教材用这个例子说明"先转换再运算"和"先运算再转换"的区别：

int auks, bats, coots;
auks = 19.99 + 11.99;              // 先按 double 加 = 31.98，再转 int → 31
bats = (int)19.99 + (int)11.99;    // 各自砍成 19 和 11，再相加 → 30
coots = int(19.99) + int(11.99);   // 同上 → 30

运行结果（教材 p84）：auks = 31, bats = 30, coots = 30。

这就是那个结论：转换的位置决定了结果。

10.5 复习题第 9 题：两条语句不等价

double x1 = 3.9, x2 = 4.9;
int sum1 = (int)x1 + (int)x2;      // 3 + 4 = 7      ← 小数被各自砍掉
int sum2 = (int)(x1 + x2);         // (int)8.8 = 8   ← 先加再砍

实测差 1。这就是"先转换再运算"和"先运算再转换"的区别。

(int)x1 + (int)x2         (int)(x1 + x2)
  3    +    4                (int) 8.8
      7                          8

为什么会差 1？ 因为 0.9 + 0.9 = 1.8，两个小数部分加起来"够进一位"了。 如果小数部分加起来不到 1，两种写法的结果就会相同。

🔍 一个重要的方法论：选测试数据本身就是一门学问。 如果当初选的是 x1 = 3.7, x2 = 4.2（小数部分 0.7+0.2=0.9，不够进位）， 两种写法会碰巧都等于 7，完全看不出差别：

(int)3.7 + (int)4.2 = 3 + 4 = 7 (int)(3.7 + 4.2) = (int)7.9 = 7 ← 一样！

要选那些能"暴露差别"的数据。 写测试、做验证时，永远问自己一句： "如果我的代码是错的，这组数据能让我发现吗？" 如果答案是不能，那这组数据就没起到验证作用。

11. auto 的陷阱（3.4.5，p83–85）

11.1 auto 是什么

C++11 新增的功能：让编译器根据初始值自动推断变量类型。

auto n = 100;        // n is int
auto x = 1.5;        // x is double
auto y = 1.3e12L;    // y is long double

（以上是教材 p84 的原例。）

auto 不是"万能类型"，它只是省了你写类型名的功夫——类型在编译期就定死了，而且由初始值决定。

11.2 ⭐ 教材 p85 专门警告的那个陷阱

跑 示例代码/03_xxx/06_auto_trap.cpp，注意教材 p85 专门警告的这个：

auto   x = 0.0;      // double ✅
double y = 0;        // double ✅（显式声明了类型，0 会自动转换）
auto   z = 0;        // ❌ int！因为 0 是 int

实测类型（用 typeid().name() 看出来）：

auto x = 0.0;   -> d (double)
double y = 0;   -> d (double)
auto z = 0;     -> i (int)  ← 踩坑

教材 p85 的原话大意：显式地声明类型时，将变量初始化为 0（而不是 0.0）不会导致任何问题， 但采用自动类型推断时，这却会导致问题。

规律：double y = 0; 是安全的（你告诉了编译器类型，它会转换）； auto z = 0; 是危险的（字面值的写法决定了类型）。

为什么危险？ 因为后面所有基于 z 的运算都变成整数运算了：

auto z = 0;
z = 1 / 2;          // 0！因为 z 是 int，1/2 是整数除法
double w = 0;
w = 1 / 2;          // 还是 0 —— 注意！右边的 1/2 先算成 0 了
w = 1.0 / 2;        // 0.5 ✅

11.3 复习题第 10 题：这些变量是什么类型

教材复习题第 10 题（这些变量是什么类型）实测：

写法 类型
auto a = 15; int
auto b = 150.37f; float（因为后缀 f）
auto c = 'B'; char
auto d = 8.25f / 2.5; double（float 和 double 运算，提升为 double）

每题的理由：

写法 为什么是这个类型
auto a = 15; 15 没后缀 → int
auto b = 150.37f; 有 f 后缀 → float
auto c = 'B'; 单引号字符字面值 → char
auto d = 8.25f / 2.5; 8.25f 是 float，2.5 是 double，混合运算向大的提升 → double

第 4 条是关键规律：float 和 double 混在一起算，结果一定是 double（提升方向是"向精度高的"）。

教材复习题第 4 题：33L 和 33 的区别——值一样，类型不同（long vs int）。 当数值超过 int 范围时，写不写 L 就决定成败。

11.4 用 auto 的时候要注意什么

场景 建议
auto x = 0;（想要小数） ❌ 写成 auto x = 0.0; 或 double x = 0;
auto 接收函数返回值 ⚠️ 先确认函数返回的类型
想让代码更可读 类型名短的时候直接写类型名，auto 反而增加推理负担
类型名长得离谱 ✅ 用 auto

auto 什么时候真有用？ 类型名长得离谱的时候：

std::vector<double>::iterator p = v.begin();   // 老写法，啰嗦
auto p = v.begin();                             // C++11，清爽

（等学到 STL 容器（第 16 章）时你会体会到。）

一条实用原则：当你需要读者一眼看出类型时，别用 auto；当类型是显而易见的或者是无关细节时，用 auto。

关于教材 p87 练习 7 的一个勘误（方法论比题目本身更重要）

教材 p87 练习 7 印的是「1 加仑 = 3.875 升」，但这个数字和教材自己给的例子对不上。 正确值是 3.785 升（美国加仑）。

用哪个因子 19 mpg 算出来 教材说
62.14 × 3.875（教材印的） 12.67 约 12.4 ❌
62.14 × 3.785（美国加仑真值） 12.38 约 12.4 ✅

27 mpg 同样：3.875 → 8.92（教材说 8.7）；3.785 → 8.71 ✅

从教材的例子反推因子：12.4 × 19 = 235.6、8.7 × 27 = 234.9， 都指向 235.2 = 62.14 × 3.785。所以是 3.875 印错了，应为 3.785。

📌 比这道题更重要的是这个方法论

教材给的「输入 → 输出」例子，就是你的验证标准。 把公式代进去算一遍，对不上就先怀疑公式或教材——不要怀疑自己。 这次就是靠这个方法发现印错的。

写出代码后，用题目给的这两组数做验证。如果算出来对不上，先别改代码， 先把公式和题目给的数据代进去手算一遍。
