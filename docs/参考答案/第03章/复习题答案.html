一、任务 2 的 4 个实验

实验 A：整数除法的「顺序陷阱」

参考答案

cout << 5 / 2 * 2 << endl;      // 4
cout << 5 * 2 / 2 << endl;      // 5
cout << 5 / 2.0 * 2 << endl;    // 5

/ 和 * 优先级相同，按从左到右结合。所以 5 / 2 * 2 先算 5 / 2： 两个操作数都是 int → 整数除法，得到 2（不是 2.5），再 2 * 2 = 4。

  • 第 2 个：5 * 2 = 10 → 10 / 2 = 5，中间结果没被截断，所以是 5。
  • 第 3 个：2.0 是 double，5 / 2.0 = 2.5 按浮点算，再 * 2 = 5.0。

要点：整数除法的截断发生在每一步中间结果上，不是只看最终结果。

原始作答记录

因为是int类型，小数直接被截断了

核对结果

  • 方向 ✅ 对：说到了「int 类型」和「小数被截断」。
  • 但没点出结合顺序这一步——为什么是 5 / 2 先算、而不是 2 * 2 先算？这才是本题的关键。

订正说明：原答案写的是「因为是int类型，小数直接被截断了」，正确应为 「/ 和 * 同级、从左到右结合，所以先算 5 / 2；两个 int 相除结果取整为 2， 再 2 * 2 = 4」，因为只说「int 截断」无法解释为什么第 2 行 5 * 2 / 2 就是 5 ——那两行全是 int，差别只在截断发生在哪一步。这也是复习题第 8 题的同一个知识点。

实验 C：浮点数能不能用 == 比

参考答案

a == b  的结果: 0
相差多少: 5.55112e-17

原因：0.1、0.2、0.3 在二进制里都是无限循环小数，只能存近似值。 0.1 + 0.2 的舍入结果与 0.3 的存储值在最低几位上不同，差约 5.55e-17， 所以 == 判定为 false。

正确比较方式：不比相等，比差值的绝对值是否小于容差。

#include <cmath>
const double EPS = 1e-9;
bool equal = std::fabs(a - b) < EPS;

原始作答记录

a == b 的结果: 0 相差多少: 5.55112e-17，因为0.1加0.2的浮点运算有精度误差，不完全等于0.3所以是false

核对结果

  • 数据 ✅ 两个输出值都对。
  • 原因 ✅ 正确：确实是二进制近似造成的精度误差。

订正说明：这一条原答案是对的，保留。只补一个更准确的说法： 0.1 + 0.2 的精确值是 0.30000000000000004440892098500626...， 而 0.3 存的是 0.299999999999999988897769753748...—— 两个近似值一个略大、一个略小，所以既不相等，也无法靠"补齐位数"解决。 另外题目还问了「该怎么比较两个浮点数」，原答案没答这部分，正确做法是 用两者差值的绝对值与一个足够小的容差比较（见上）。

实验 D：unsigned 的陷阱

参考答案

5u - 10u = 4294967291

if (u - v > 0) 成立，会打印「居然进来了！」。

为什么 5 减 10 会得到那么大一个数：

  • unsigned int 是 32 位，取值范围 0 ~ 4294967295（即 2³² − 1）。
  • 无符号运算的结果按 2³² 取模：5 - 10 = -5，-5 + 2³² = 4294967291。 （换个说法：从 0 再往下走就绕回最大值——5 - 5 = 0，减 1 绕到 4294967295，再减 4 得 4294967291。）
  • u - v 的类型是 unsigned int，无符号数永远 ≥ 0，所以 u - v > 0 恒为真。 这才是这个陷阱最危险的地方：判断条件写错不会报错，只是结果莫名其妙。

原始作答记录

你的猜测：42亿

实际答：5u - 10u = 4294967291

为什么：因为两个无符号的数，小的减去大的，就直接挑到另一端了，又因为是无符号，最大值为原来有符号位的两倍，所以还是42亿多

核对结果

  • 猜测 ✅ 对（42 亿量级）；实测值 ✅ 完全正确（4294967291）。
  • 原因 ✅ 方向正确：「小的减大的就绕到另一端」就是按 2³² 取模的通俗说法。
  • ⚠️ 「最大值为原来有符号位的两倍」这个说法不精确，应为「两倍加一」。
  • ❌ 漏了最关键的一问：if 会不会成立？ 答案见下。

订正说明：原答案写的是「最大值为原来有符号位的两倍」，正确应为 「无符号类型的最大值 = 同宽度有符号类型最大值的 2 倍 + 1」， 因为有符号 int 最大是 2147483647（2³¹ − 1），无符号最大是 4294967295（2³² − 1）， 4294967295 = 2 × 2147483647 + 1。差的这个 1 就是「0」占的那一个位置。 另外原答案漏答了实验里最关键的一问：if (u - v > 0) 会成立，会打印「居然进来了！」， 因为 u - v 是无符号数、永远 ≥ 0，这个条件恒为真——这一点值得单独记住。

第 1 题：为什么 C++ 有多种整型？

不同整型在占用的内存大小和能表示的数值范围上不同。 这样可以针对具体用途选择最省空间、最合适的类型， 也便于在不同字长的平台上书写可移植的代码。

原始作答记录

不同整型在占用内存大小和可表示的数值范围上不同

核对结果

  • ✅ 完全正确，保留。

第 2 题：声明与描述相符的变量

参考答案

a. short 整数，值为 80

short x = 80;

b. unsigned int 整数，值为 42110

unsigned int x = 42110;

c. 值为 3000000000 的整数

long long x = 3000000000;      // 教材附录 J 给的答案还可用 unsigned long

原始作答记录

a. short x = 80; b. unsingned int x = 42110 c. long long x = 3000000000;

核对结果

  • a ✅ 完全正确。
  • b ❌ 拼写错 + 漏分号（见订正说明）。
  • c ✅ 正确、可接受。

订正说明：原答案 b 写的是 unsingned int x = 42110， 正确应为 unsigned int x = 42110;，因为 ① unsingned 拼写错了，正确拼写是 unsigned（signed 前面加 un-，不是 singned）； ② 语句末尾漏了分号 ;，C++ 每条声明语句都必须以分号结尾，漏掉会直接报编译错误。

补充（c 的一个细节）：3000000000 大于 INT_MAX（2147483647），所以不能用 int。 这个字面量本身的类型由编译器按 int → long → long long 的顺序取第一个装得下的： 在 long 为 64 位的平台（如 64 位 Linux）上它是 long，在 long 为 32 位的平台 （如 Windows / MinGW）上它是 long long。所以写 long long 是安全的。

第 3 题：C++ 提供了什么措施来防止超出整型的范围？

参考答案

  • 运行时：C++ 不做任何检查。 溢出时结果按「模 2ⁿ」回绕 （有符号溢出严格来说是未定义行为，实践中多数平台表现为回绕成负数）， 不会报错、不会抛异常。
  • 编译期：能帮上一点忙。 用 auto 让编译器根据字面量选一个装得下的类型， 可以避开「字面量本身太大」这一种溢出；明确写 unsigned / long long 也是办法。
  • 编程习惯： 选足够宽的类型，运算前预判范围，必要时用 <limits> 里的 std::numeric_limits<T>::max() 自己检查。

一句话：语言不管，责任在程序员。

原始作答记录

没有措施

核对结果

  • 方向 ✅ 对：核心意思「没有（运行时）自动检查」抓住了。
  • 但答得太绝对，漏了编译期能做的规避手段，也没说清「溢出以后会发生什么」。

订正说明：原答案写的是「没有措施」，正确应为 「运行时没有任何检查，溢出会默默回绕；但编译期可以用 auto、显式指定更宽的类型、 或用 numeric_limits 自查来规避」，因为说「没有措施」会让人以为完全无从下手 ——实际上语言确实不检查（这是要记住的重点）， 但选类型和预判范围正是程序员的责任。 此处建议对照教材附录 J（p933）核对该题的官方措辞。

第 5 题：char grade = 65; 与 char grade = 'A'; 是否等价？

参考答案

char grade = 65;
char grade = 'A';

在 ASCII 平台上等价。

因为 65 正好是字符 'A' 在 ASCII 中的编码，把整数赋给 char 时会隐式转换成 对应编码的字符，所以两条语句效果完全相同。

严格来说这是实现定义的：如果平台用的不是 ASCII（例如某些 EBCDIC 机器）， 65 就不一定是 'A'。不过现代平台几乎都是 ASCII，可以认为成立。

原始作答记录

等价

核对结果

  • ✅ 正确，保留。

订正说明：这一条原答案是对的，只补一句更严谨的限定： 「等价」的前提是平台使用 ASCII 编码，因为 65 这个数字本身没有"字符"含义， 是 ASCII 规定了 65 ↔ 'A'。教材也强调过这一点。 此处建议对照教材附录 J（p933）核对措辞。

第 6 题：如何找出编码 88 表示的字符？至少两种方法

参考答案

答案本身：编码 88 表示的字符是 'X'。

方法 1：把整数赋给 char 变量再输出

char ch = 88;
std::cout << ch << std::endl;      // X

方法 2：强制类型转换 (char)88

std::cout << (char)88 << std::endl;                    // X
std::cout << static_cast<char>(88) << std::endl;       // X（C++ 风格）

方法 3（另一种可行思路）：把 char 提升为整数来「对表」

for (int i = 0; i < 128; ++i)
    std::cout << i << " -> " << (char)i << '\n';       // 88 那一行就是答案

原始作答记录

方法 1：直接让88赋值给char，再输出char 方法 2：给char赋值，一个一个推

核对结果

  • 方法 1 ✅ 对，就是「把 88 赋给 char 再输出」，表述含糊但路子正确。
  • 方法 2 ❌ 不是方法（见订正说明）。

订正说明：原答案方法 2 写的是「给 char 赋值，一个一个推」， 正确应为「强制类型转换 (char)88」，因为「一个一个推」是人工试错， 不是编程方法——题目问的是"如何使用 C++ 找出"，必须给出可执行的代码手段。 (char)88 之所以算独立的第二种方法，是因为它不需要额外声明变量， 是在表达式内部做显式类型转换，和「赋给变量」是两条不同的语法路径。 （也可写 static_cast<char>(88)。） 更省事的第三种思路是用循环遍历 0~127 打印整数与字符的对照表，一看便知。

第 7 题：long → float / double，long long → double

参考答案

C 类型 有效位数（尾数） 能精确表示的连续整数上限
float 24 位 16777216（约 1.67×10⁷）
double 53 位 9007199254740992（约 9×10¹⁵，即 2⁵³）
long double（x86） 64 位 约 1.8×10¹⁹
  • long 在 32 位环境是 32 位，最大值 2147483647 ≈ 2.1×10⁹，远小于 2²⁴， 所以连 float 都能精确表示；赋给 double 当然更没有误差。
  • long long 是 64 位，最大约 9.2×10¹⁸，超过 2⁵³ ≈ 9×10¹⁵， 所以赋给 double 时超过 2⁵³ 的那部分整数会损失精度（会有舍入误差）。

判断方法：比较该整型能取到的最大值和浮点类型能精确表示的整数上限。

原始作答记录

long赋给double不会误差，double保证53位精度，longlong有64位，会导致误差

核对结果

  • ✅ 完全正确，保留并肯定。 「double 保证 53 位精度」「long long 有 64 位所以会误差」 两个关键判断都对了，只差把「53 位」的含义点明。

订正说明：这一条原答案是对的，保留。只补充说明： 所谓「53 位」指的是 double 的尾数（有效数字）位数，不是这个类型的大小 （double 本身占 64 位 = 1 符号位 + 11 指数位 + 52 显式尾数位，加上隐含的 1 位共 53 位有效数字）。 之所以 long long → double 会出问题，正是因为 64 位的 long long 能取到的值 超过了 53 位能精确表示的上限 2⁵³ ≈ 9×10¹⁵。

第 8 题：下列表达式的结果

参考答案

表达式 结果 计算过程
a. 8 * 9 + 2 74 72 + 2（* 优先级高于 +）
b. 6 * 3 / 4 4 18 / 4 → 整数除法截断成 4（真值 4.5）
c. 3 / 4 * 6 0 3 / 4 → 先截断成 0，再 0 * 6 = 0
d. 6.0 * 3 / 4 4.5 18.0 / 4，有 double 参与 → 浮点除法
e. 15 % 4 3 15 = 4×3 + 3，取余数

b 和 c 数字一样，为什么结果不同？

关键在于「整数除法从左到右结合，中间结果被截断」：

b.  6 * 3 / 4   →  先 6*3 = 18    →  18 / 4 = 4     （4.5 被截断成 4）
c.  3 / 4 * 6   →  先 3/4 = 0     →  0 * 6  = 0     （0.75 先被截断成 0）

原始作答记录

预判与实测表：a=44 / 44，b=4 / 4，c=0 / 0，d=4.5 / 4.5，e=3 / 3

b 和 c 为什么不同：两个整型的数相除，小数直接被舍弃了,3/4 = 0

核对结果

  • a ❌ 数值错：正确是 74（见订正说明）。
  • b、c、d、e ✅ 全部正确。
  • 「为什么不同」⚠️ 结论对，但没说到关键点：没提「从左到右」和「中间结果」。

订正说明：原答案 a 栏写的是 44，正确应为 74， 因为 8 * 9 + 2 里乘号优先级高于加号，先算 8 * 9 = 72，再 72 + 2 = 74。 而且 a 栏的「实测」也写的 44——实测栏本应是 74，跑一遍代码就能发现。 （44 不是任何自然分组的乘积：8 × (9 + 2) = 88，(8 + 9) × 2 = 34， 所以这不是算错顺序，而是算错了 8×9。）

关于 b、c 的追问：原答案写的是「两个整型的数相除，小数直接被舍弃了」， 方向正确，但正确表述应为「整数除法从左到右结合，中间结果被截断」—— c 里第一个运算就是整数除法 3 / 4，中间结果 0.75 当场被截断成 0， 后面的 * 6 再乘也还是 0；而 b 里第一个运算是乘法，中间结果 18 是整数、没有损失， 直到 / 4 才截断一次。这题与浮点精度毫无关系，两个操作数从头到尾都是 int， 根本没用到浮点数。这也正是任务 5.1 的同一个问题。

第 9 题：把两个 double 作为整数相加

参考答案

// ① 作为整数相加（先各自截断，再相加）
int sum = static_cast<int>(x1) + static_cast<int>(x2);

// ② 作为 double 相加后再转 int（先相加，再截断）
int sum = static_cast<int>(x1 + x2);

C 风格写法 (int)x1 + (int)x2 和 (int)(x1 + x2) 效果完全相同，教材用的就是这种。

原始作答记录

作为整数相加：int sum = int(x1) + int(x2); 作为 double 相加再转换：int sum = int(x1 + x2);

核对结果

  • ✅ 完全正确，保留。 两种写法都对，而且正确区分了截断发生的位置。

订正说明：这一条原答案是对的。int(x1) 这种写法叫函数式强制转换， 在 C++ 里合法（效果等同 (int)x1）；更推荐 static_cast<int>(x1) 的写法， 因为它在代码里好找、也不容易看漏。这个区别正好是任务 5.4 考的点。

第 10 题：auto 声明的变量类型（用 typeid().name() 验证）

参考答案

小题 语句 类型 原因
a auto cars = 15; int 整数字面量默认 int
b auto iou = 150.37f; float 后缀 f 指定为 float
c auto level = 'B'; char 字符字面量是 char（1 字节）
d auto crat = U'\U00002155'; char32_t 前缀 U + 8 位 \U 转义 → UTF-32 码元（4 字节）
e auto fract = 8.25f/2.5; double float / double 按类型提升结果为 double

关键是 d：字符字面量的类型由前缀决定。

字面量写法 类型 大小（本平台）
'\U00002155' char 1 字节
u'\U00002155' char16_t 2 字节
U'\U00002155' char32_t 4 字节
L'\U00002155' wchar_t 2 字节（Windows）

原始作答记录

预判：a=int，b=float，c=字符，d=字符，e=double 实测：a=int，b=float，c=char，d=char32_t，e=double

核对结果

  • a ✅ 正确。
  • b ✅ 正确。
  • c ✅ 正确（「字符」的精确类型名是 char）。
  • d ❌ 错（见订正说明）。
  • e ✅ 正确。

订正说明：原答案 d 栏写的是「字符」，正确应为 char32_t， 因为 U'\U00002155' 用的是 U 前缀（UTF-32 字符字面量）配 8 位十六进制 \U 转义， 类型完全由前缀决定：U → char32_t（4 字节）、u → char16_t（2 字节）、 L → wchar_t、无前缀 → char（1 字节）。 而且 \U00002155 这个码点需要 4 字节才装得下，char 只有 1 字节、根本表示不了， 所以绝不可能是 char。（原答案的「实测」栏已经写对了 char32_t， 但「你的答案」栏写的是「字符」，说明当时是靠实测纠正的，没抓到"前缀决定类型"这条规律。）

另外 e 栏的机制值得记住：8.25f 是 float、2.5 是 double， 混合运算按「低精度向高精度提升」的规则变成 double / double，结果是 double ——这正是本章「隐式类型转换（类型提升）」的典型例子。

三、任务 5：过关自测

5.1 6*3/4 和 3/4*6 的结果及原因

参考答案

6 * 3 / 4  = 4
3 / 4 * 6  = 0

原因：/ 与 * 同级、从左到右结合。 3 / 4 * 6 的第一个中间结果 3/4 是整数除法，0.75 被截断成 0， 后面再乘 6 也还是 0。而 6 * 3 / 4 先算出整数 18，只在最后一步 / 4 截断一次 （18/4 = 4.5 → 4）。与浮点精度无关，只与整数除法的中间结果截断有关。

原始作答记录

63/4 = 4 3/46 = 0 因为6*3=18,连个整型的数相除，小数直接被舍弃了，同理3/4 = 0

核对结果

  • 两个结果 ✅ 正确。
  • 思路 ✅ 正确。

订正说明：这一条原答案结果和思路都对，保留。 只建议把表述往「中间结果」和「从左到右」上靠： 说清「3/4 是先算的，它一截断成 0，后面的乘法就无可挽回了」—— 这样才解释得清为什么 b 题（同是 6、3、4）能得 4，而 c 题只能得 0。

5.2 总秒数 → 天/时/分/秒

参考答案

const long long SEC_PER_MINUTE = 60;
const long long SEC_PER_HOUR   = 60 * SEC_PER_MINUTE;   // 3600
const long long SEC_PER_DAY    = 24 * SEC_PER_HOUR;     // 86400

long long days    = total_seconds / SEC_PER_DAY;
long long rest    = total_seconds % SEC_PER_DAY;
long long hours   = rest / SEC_PER_HOUR;
rest              = rest % SEC_PER_HOUR;
long long minutes = rest / SEC_PER_MINUTE;
long long seconds = rest % SEC_PER_MINUTE;

注意点：

  • 每一层都是「先除得商、再取模得余数」，这就是 /% 配对的经典模式。
  • 最后一步用 % 60 或直接用剩余值都可以（此时 rest 必然 < 60）。
  • 变量建议用 long long（或 long）：31600000 虽然装得进 int，但秒数很容易越界。
  • 按教材要求，86400、3600、60 应该用 const 符号常量表示，不要直接写数字。

原始作答记录

day = total_seconds / sec_per_day;
total_seconds = total_seconds % sec_per_day;
hours = total_seconds / sec_per_hour;
total_seconds = total_seconds % sec_per_hour;
minutes = total_seconds / sec_per_minutes;
total_seconds = total_seconds % sec_per_minutes;
seconds = total_seconds;

核对结果

  • ✅ 思路和代码完全正确，保留。 「先除、再取模」的节奏完全对， 最后一层直接用剩余值也对（此时它必然小于 60）。

订正说明：这一条原答案是对的，只有两处风格建议，不算错误： ① sec_per_minutes 建议改成 SEC_PER_MINUTE（「一分钟」只有一分钟，不该用复数； 常量名一般全大写）； ② 代码里用到的 sec_per_day、sec_per_hour 这些名字要先用 const 定义好 （本题的题目要求明确说「用符号常量」），不要写成数字字面量。

5.3 为什么 0.1 + 0.2 == 0.3 是 false？该怎么比较浮点数？

参考答案

原因：0.1、0.2、0.3 的二进制表示都是无限循环小数，只能存成近似值。 0.1 + 0.2 的舍入结果与 0.3 的存储值在最低几位上不同，差值约 5.55112e-17， 所以 == 判定为 false。

正确比较方式：不比相等，比差值的绝对值是否小于容差。

#include <cmath>
const double EPS = 1e-9;
if (std::fabs(a - b) < EPS)
    std::cout << "可以认为相等" << std::endl;

原始作答记录

因为浮点数有精度的，0.1 + 0.2 = 0.300**04 所以是false，应该比较的是两个浮点数想减小于等于他们的进度误差

核对结果

  • 结论 ✅ 正确：确实因为浮点精度，不能用 ==。
  • 做法 ✅ 正确：确实是「相减后与误差/容差比较」——这题的核心答对了。
  • 表述 ❌ 有三处笔误要改（见订正说明）。

订正说明：原答案写的是「0.1 + 0.2 = 0.300**04」， 正确应为 0.30000000000000004——0.1 + 0.2 的精确值是 0.30000000000000004440892098500626...，双精度舍入后约 0.30000000000000004。 而且关键不在于「多了个小尾巴」，而在于 0.3 存的是略小于 0.3 的 0.299999999999999988897769753748...——两个近似值一个偏大、一个偏小，所以永不相等。 另外两处用词要改：原答案的「进度误差」应为「精度误差（容差 / epsilon）」， 「想减」应为「相减」。做法本身原答案说对了，保留。

5.4 (int)x1 + (int)x2 和 (int)(x1 + x2) 有什么区别？

参考答案

两种写法截断发生的位置不同，结果可能不同：

double x1 = 1.9, x2 = 2.9;
int a = (int)x1 + (int)x2;    // 1 + 2     = 3
int b = (int)(x1 + x2);       // (int)4.8  = 4
  • (int)x1 + (int)x2：先各自截断，再相加。
  • (int)(x1 + x2)：先相加，再截断。

cast 的优先级高于 +，所以第一种写法里两个 (int) 各自先起作用。

原始作答记录

第一个是先把x1 和x2分别转化为整型再进行相加操作，第二个是先进行相加操作再转化为整型

核对结果

  • ✅ 完全正确，保留。

订正说明：这一条原答案是对的。可以补一个具体数字感受差别 （x1 = 1.9, x2 = 2.9 时，前者得 3、后者得 4）， 这个例子也正好说明截断位置会影响结果，和复习题第 9 题是同一个点。

附：本章要记住的三句

  1. 两个整数相除，结果还是整数，小数部分被截断（不是四舍五入）， 而且截断发生在每一步中间结果上。
  2. 要得到小数结果，必须让除法的两个操作数里至少有一个是浮点数 （写法：(double)a / b，或 a / 2.0）。复习题第 8、9 题和编程练习 3、5 都在考这一点。
  3. 教材给的「输入 → 输出」例子就是验证标准：代进去算一遍，对不上先怀疑公式或教材 （练习 7 的 3.875 就是印错的，应为 3.785）。
