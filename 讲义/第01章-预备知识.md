## 1. 零基础补白（一）：编程语言是什么，为什么需要它

### 1.1 人和计算机没法直接说话

计算机的 CPU 只会做一件事：执行**机器指令**。这些指令长这样（十六进制字节）：

```
48 8B 05 B1 1A 00 00
```

它是纯粹的数字，表示「把内存某个地址的数据读到寄存器里」。**人类没法用这个写程序**——写 100 行就崩溃了，而且没人能看懂。

所以中间必须有翻译层。**编程语言就是这层翻译**：

| 层次 | 谁看得懂 | 例子 |
|---|---|---|
| 机器语言 | 只有 CPU | `48 8B 05 ...` |
| 汇编语言 | 少数人，和机器一一对应 | `movq .LC0(%rip), %rsi` |
| 高级语言 | 人 | `std::cout << "hi";` |

「高级」的意思不是「厉害」，而是**离人类近、离机器远**。

### 1.2 一句话总结

> **编程语言 = 一套让人类能精确描述「要计算机做什么」的规则，同时有工具能把它翻译成机器指令。**

「精确」这个词很重要。自然语言说「把数组里最大的数找出来」，计算机听不懂；编程语言要求你把这件事拆成一步步明确的操作。**学编程，主要就是学怎么把想法拆到这么细。**

### 1.3 C++ 在这张地图上的位置

C++ 是一门**编译型**的、**静态类型**的、**多范式**的编程语言。

这三个词都是对比出来的，下面逐个拆开讲。

## 2. C++ 是什么：三个词和一张对比表

| 术语 | 白话解释 |
|---|---|
| **编译型** | 写完之后要先用一个叫「编译器」的程序**整体翻译**成机器码，才能运行 |
| **静态类型** | 变量是什么类型（整数？文字？小数？）**必须在写代码时就写明**，编译器会检查 |
| **多范式** | 支持多种写程序的风格（面向过程、面向对象、泛型），你可以混着用 |

对比着看最清楚。即使你没学过 Python，看这张表也能理解差异在哪：

| | Python（解释型语言） | C++（编译型语言） |
|---|---|---|
| 怎么变成能跑的程序 | 解释器逐行读、逐行执行 | **先由编译器翻译成机器码**，再运行 |
| 类型什么时候确定 | 运行时才知道（`a = 1` 之后再 `a = "x"` 也行） | **编译期就确定**，`int a` 之后不能装字符串 |
| 变量要不要声明 | 不用 | **必须声明**，还要写类型 |
| 出错时机 | 跑到那行才崩 | **编译时就报错**，大部分错误根本生不出 exe |
| 速度 | 慢（有解释开销） | 快（接近直接操作硬件） |
| 内存管理 | 自动（垃圾回收） | **基本靠手动**（第 4、12 章重点，也是 C++ 最难的部分） |

**为什么值得学 C++**：它让你能看见其他语言帮你藏起来的一切——内存、类型、编译。学完 C++ 再回头看别的语言，你会知道它在替你做什么。

> 📌 表里「exe」这个词后面会反复出现。它就是 Windows 上的**可执行文件**（executable），双击就能运行的东西。现在只需要记住这个名字。

## 3. 零基础补白（二）：源代码、编译器、可执行文件

这三个东西是本章的主角，先用生活化的比方讲清楚它们的关系。

### 3.1 一个比方：中文菜谱 → 英文菜谱 → 厨师做菜

| 角色 | 比方里是谁 | 在 C++ 里是什么 |
|---|---|---|
| 你写的文字 | 中文菜谱 | **源代码**（`.cpp` 文件） |
| 翻译 | 把中文菜谱翻成英文的人 | **编译器**（compiler，比如 `g++`） |
| 翻译结果 | 英文菜谱 | **机器码 / 目标文件 / 可执行文件** |
| 执行 | 只会英文的厨师 | **CPU** |

关键点：

- **厨师只看得懂英文菜谱**，也就是 CPU 只认机器码。你写的中文（C++ 源码）写得再好，厨师看不懂。
- **翻译是一整本一起翻的**，不是做一步翻一句。这就是「编译型」。
- 翻译过程中如果发现菜谱里写了「先放盐再打鸡蛋」但你没买鸡蛋，**翻译的人当场就会指出问题**，根本轮不到厨师下厨。这就是「编译期就能报错」。

### 3.2 源代码（source code）

- 就是你用键盘敲进文件里的那些文字，是**纯文本**，可以用记事本打开
- C++ 源文件的扩展名用 **`.cpp`**（也有人用 `.cxx`、`.cc`、`.C`）
- 源文件是给**人**看的，也是给**编译器**看的。它本身**不能运行**——双击 `.cpp` 什么也不会发生

### 3.3 编译器（compiler）

- 一个**程序**，不是 VS Code 的一部分，也不是操作系统自带的
- 输入：`.cpp` 源文件。输出：机器码文件
- 它不关心你的文件名、不关心你怎么排版（缩进几个空格随你），**只看内容**
- 它的工作分成几步（第 6 节详细讲），其中一步会把 `#include` 的内容整段复制进来
- **它会在翻译过程中检查语法和类型**，发现问题就打印「报错」并停止，不产出可执行文件

### 3.4 可执行文件（executable）

- Windows 上是 `.exe`，Linux/macOS 上没有扩展名或叫别的名字
- 里面是**机器码**，可以直接交给 CPU 跑
- **它和你写的源码已经没有直接关系了**：改源码必须重新编译才会体现在 exe 里
- 它通常比源码大很多（因为里面塞进了别人写好的现成代码，第 6 节会用真实数字证明）

### 3.5 一条必须记住的因果链

```
源代码(.cpp)  ──编译器──▶  可执行文件(.exe)  ──双击/命令行──▶  程序运行
     │                              │
  改这里                       改这里没用
  ↓
  必须重新编译
```

> 💡 **初学者最常问的问题**：「我改了代码，为什么运行结果没变？」
> 九成是因为**没重新编译**——你运行的是旧的 exe，或者是在调试器里跑着旧版本。

## 4. 零基础补白（三）：C++ 为什么要「编译」，Python 不用

前面说 C++ 是编译型、Python 是解释型，这里把两条路线并排摆出来看。

### 4.1 两条路线

| | 编译型（C++、C、Rust、Go） | 解释型（Python、JavaScript、Ruby） |
|---|---|---|
| 谁在执行 | CPU 直接执行机器码 | 一个叫「解释器」的程序读一行、执行一行 |
| 什么时候翻译 | **运行之前**，一次性全翻完 | **运行时**，边读边翻边执行 |
| 中间产物 | `.exe` 文件，可以单独拿走 | 没有，必须带着解释器一起 |
| 发程序给别人 | 发 `.exe`，对方不用装编译器 | 对方必须装好 Python 和所有依赖库 |
| 发现错误 | 编译时就能发现语法/类型错误 | 只有跑到那一行才发现 |
| 速度 | 快 | 慢（每次执行都要现场翻译） |

### 4.2 一句直觉化的解释

- **编译型 = 提前把整本书翻译好，出版纸质书**。读者拿起来就能读，读得快。缺点是出版一次要等（编译要时间），而且改一个字就要重印（重新编译）。
- **解释型 = 现场同声传译**。改一个字立刻能讲，很灵活。缺点是每次讲都要现场翻，慢，而且翻译翻错了要等讲到那句才知道。

### 4.3 各自的代价

| | 好处 | 代价 |
|---|---|---|
| 编译 | 跑得快、错误早发现、能脱离编译器分发 | 每次改代码都要重新编译（大项目编译几分钟很正常） |
| 解释 | 改完立刻能跑、写得快 | 慢、错误发现得晚、运行环境依赖多 |

> 📌 **C++ 也不是完全没有「解释」的成分**：报错信息里的行号、`#include` 的展开时机等，都牵涉到「预处理」这个更早的阶段。第 6 节会把这些拆开。

### 4.4 为什么本书选 C++ 而不是直接学 Python / Java

这不是「C++ 更高级」的问题，而是**你想看见什么**的问题：

| 你的诉求 | 更合适的起点 | 理由 |
|---|---|---|
| 想快速做出个小工具，不想管内存 | Python | 库多、语法短，几十行见效 |
| 想理解「程序到底怎么跑的」 | C++ | 内存、类型、编译、链接全都摆在明面上，藏不住 |
| 想写好大型长期维护的系统 | Java / C# / Go | 生态和工程工具更省心 |
| 想写游戏引擎、操作系统、高性能计算 | C++ | 性能可控、没有运行时负担 |

**学 C++ 的核心收益是「透明」**：在其他语言里你要靠猜的东西（这个变量占几个字节？这个对象什么时候销毁？这个函数调用要走多远？），在 C++ 里都有明确答案。这份透明感会让你之后学任何语言都更快。

## 5. C++ 的三个思想来源（教材 1.2，p19–21）

C++ 不是一个天才一拍脑袋设计出来的语言，它是**三种编程思想层层叠加**的结果。理解这一点，就能理解为什么 C++ 有的地方像 C、有的地方像 Java。

| 来源 | 诞生 | 核心思想 | 在 C++ 里长什么样 |
|---|---|---|---|
| **C 语言** | 1972，Dennis Ritchie，贝尔实验室（为了写 UNIX） | **结构化编程**：把大程序拆成小任务（函数），自顶向下设计 | `int main()`、函数、`for`/`while`、数组、指针 |
| **面向对象编程** | 1960s–70s（Simula 67、Smalltalk） | **类与对象**：把数据和操作数据的函数捆在一起；封装、继承、多态 | `class`、`public`/`private`、构造函数、虚函数 |
| **泛型编程** | 1990s（Alexander Stepanov 的 STL） | **模板**：写不依赖具体类型的代码，算法与数据结构分离 | `template`、`std::vector<int>`、标准模板库 STL |

### 5.1 结构化编程（1.2.2）—— 这条最重要

教材 p20 讲的核心是：**把大程序拆成若干小任务，每个任务用一个函数完成**。

「函数」在这里的白话意思是：**一段有名字、可以被反复调用的代码**。比如「打印矩阵」这件事写成一个叫 `print_matrix` 的函数，之后想打印矩阵，写一行 `print_matrix(m);` 就行了，不用把那十几行抄一遍。

这正是初学者最容易忽略、也最影响后续进步的一条。看一个真实的反面样本：一个螺旋矩阵程序，算法完全正确，但 **60 行逻辑全部写在 `main` 里**。同类写法在字符串加密、字符串类的小练习里也很常见。它**能跑**，但：

- 读代码的人（包括三个月后的你自己）得从头读到尾才知道程序在干什么
- 想单独测试「生成矩阵」这部分？做不到，它和输入输出缠在一起
- 出错时不知道是算法错了还是打印错了
- 想复用这段螺旋矩阵逻辑到别的程序？只能复制粘贴

> 📌 **为什么拿别人的代码当反面例子？**
> 因为**这不是「谁写的」的问题，而是「这样写会有什么后果」的问题**。
> 这种写法非常普遍，几乎每个人初学阶段都会写出来，所以提前认识它。
> 顺便说：**读懂别人的代码并指出问题，本身就是一项独立的能力**——
> 工作中你花在读代码上的时间，往往比写代码多。

**这就是后面会花大力气练的东西**：把程序拆成「每个函数只做一件事」。教材第 7 章整章都在讲这个。参考代码 `示例代码/01_参考_代码重构示例/spiral_functions.cpp` 里有一个把上面那种写法拆成三个函数的版本，可以先看一眼「未来的代码长什么样」——**现在不用看懂，只是为了知道我们要去哪**。

> 💡 **一条经验法则**（先记着，第 7 章会展开）：
> 一个函数**只做一件事**，长度控制在 **10–30 行**。超过 50 行就该拆了。

### 5.2 面向对象与泛型（1.2.3–1.2.4，p20–21）

- **面向对象**：类是「数据 + 操作这些数据的函数」的打包。比如一个 `Matrix` 类，自己知道自己多大、自己能打印自己，而不是让 `main` 去操心。
- **泛型**：`std::vector<int>` 和 `std::vector<double>` 是同一份模板代码生成的两个类型——不用为每种类型重写一遍。`std::vector` 是 C++ 标准库里的「可变长数组」，后面会大量使用；这里只需要知道它背后是模板。

### 5.3 C++ 的起源（1.2.5，p21）

- 1979 年，**Bjarne Stroustrup**（本贾尼·斯特劳斯特鲁普，丹麦人）在贝尔实验室开始搞，最初叫 **"C with Classes"**
- 1983 年改名 **C++**（`++` 是 C 里的自增运算符 → "C 的升级版"）
- 1998 年第一个 ISO 标准 **C++98**，之后 C++03、**C++11**、C++14、C++17、C++20

> **补充**：语言的演进不是「哪个国家的人垄断」的事。C 语言由美国人设计，但 C++ 标准委员会里有来自丹麦、瑞士、芬兰、俄罗斯、中国等各国的成员，标准库的大量组件也由不同国家的工程师贡献。**这是一项多人几十年的协作工程**，不是一个人的作品。

## 6. 可移植性和标准（教材 1.3，p22–23）

**可移植性**：源代码不改动，就能在 Windows / Linux / macOS 上**重新编译**后运行。

注意这句话里的关键词是「**重新编译**」。C++ 的可移植 ≠ 同一个 exe 到处跑，而是**同一份源码到处能编译**。这就是为什么：

- 写跨平台代码时，常常要用条件编译把某段代码「只在 Windows 上保留」——因为在 Linux 上 `<windows.h>` 根本不存在，得让**预处理器**（一个在编译最前面跑的文本处理工具）把这段代码**整体删掉**：
  ```cpp
  #if defined(_WIN32)
  // 只有 Windows 才会编译这一段
  #endif
  ```
- 写代码时尽量只用**标准库**（C++ 标准规定每个编译器都必须提供的那些功能），不用某个平台特有的东西

**关于标准版本**：教材（第 6 版）基于 **C++11**。一门课的实测编译器是 GCC 8.1.0，支持到 **C++17**。所以本课给的编译命令是 `-std=c++17`——比教材上的标准更新，教材上的所有例子都能跑，额外还能用一些新特性。

> `-std=c++17` 里的 `-std` 是「standard（标准）」的缩写，它是在告诉编译器：「请按 C++17 这套规则来检查我的代码」。

想确认自己的编译器支持哪些标准，可以自己查（这是个好习惯）：

```powershell
g++ --help=common | Select-String "std="
```

> 📌 `Select-String` 是 PowerShell 里「在输出里找包含某段文字的行」的命令，相当于在结果里搜索。

## 7. 零基础补白（四）：命令行（终端）是什么

后面要敲很多命令，如果你从没碰过命令行，先花 3 分钟看完这一节。

### 7.1 命令行是什么

平时你用鼠标双击图标、点菜单来指挥电脑，这叫**图形界面（GUI）**。
**命令行**则是「打字指挥电脑」的方式：你输入一行文字，按回车，电脑执行，然后把结果打在屏幕上。

它比图形界面难用一点，但有几个不可替代的好处：

- **能被记录、被复制**：一行命令可以原样贴进文档、笔记、给别人
- **能自动化**：几十个文件的重复操作，一条命令搞定
- **很多开发工具只有命令行接口**：编译器 `g++` 就是典型

### 7.2 怎么打开

| 系统 | 操作 |
|---|---|
| Windows | 开始菜单搜「PowerShell」或「终端」，点开；或者在 VS Code 里按 `` Ctrl+` `` 打开内置终端 |
| macOS | 打开「终端」（Terminal） |
| Linux | 打开「终端」 |

打开后你会看到一个**提示符**，比如 `PS C:\Users\name>`。它后面的文字就是**光标位置**——你打的命令出现在这里，按回车执行。

**关键认知：终端打开时，你「站在」某个文件夹里。** 这个文件夹叫**当前工作目录**。你敲的 `g++ demo.cpp` 里的 `demo.cpp`，指的就是这个文件夹下的文件。

### 7.3 两个最基础的命令：看目录、换目录

| 想做什么 | Windows PowerShell | macOS / Linux | 备注 |
|---|---|---|---|
| 看当前在哪个目录 | `pwd` | `pwd` | print working directory |
| 列出当前目录的文件 | `ls` 或 `dir` | `ls` | PowerShell 两个都认 |
| 切换目录 | `cd 目标` | `cd 目标` | change directory |
| 回到上一级 | `cd ..` | `cd ..` | `..` 表示「上一层文件夹」 |
| 回到 C 盘根目录 | `cd C:\` | `cd /` | |
| 新建文件夹 | `mkdir 名字` | `mkdir 名字` | make directory |
| 清屏 | `cls` | `clear` | 屏幕太乱时用 |

### 7.4 `cd` 的三个必知细节

1. **路径有空格时要加引号**：
   ```powershell
   cd "C:\My Projects\cpp"
   ```
   不加引号，终端会把 `My` 和 `Projects\cpp` 当成两个东西。
2. **跨盘符要分两步（Windows）**：如果当前在 `C:`，想直接去 `D:\Projects`，`cd D:\Projects` 在 PowerShell 里通常是可以的；但如果你用的是老的 `cmd.exe`，要先打 `D:` 再打 `cd \Code`。
3. **`cd` 完心里要清楚自己在哪**：不确定就敲一次 `pwd`（或 `Get-Location`）。**八成的「文件找不到」错误，都是因为在错误的目录里敲命令。**

### 7.5 相对路径 vs 绝对路径

| 写法 | 名字 | 例子 | 含义 |
|---|---|---|---|
| 从盘符开头 | 绝对路径 | `D:\Cpp练习\L01` | 不管你在哪，都指同一个地方 |
| 从当前位置开头 | 相对路径 | `示例代码\01_错误分类实验\a_syntax.cpp` | 相对于「当前工作目录」 |

**本讲义统一用相对路径**，例如：

```
示例代码/01_错误分类实验/A_missing_semicolon.cpp
```

意思是「在你当前这个讲义所在的目录下，进入 `示例代码`，再进入 `01_错误分类实验`，里面有个 `a_syntax.cpp`」。你自己组织文件时按这个结构放即可。

### 7.6 三个救命技巧

- **按 ↑ 键**可以调出上一条命令，不用重打
- **按 Tab 键**可以自动补全文件名，避免打错
- **`Ctrl+C`** 可以中断一个卡住/死循环的程序

## 8. 零基础补白（五）：写程序需要哪些工具

一个程序从「写出来」到「能运行」，需要两样东西，它们**互相独立**：

| 工具 | 干什么 | 举例 | 没有它会怎样 |
|---|---|---|---|
| **编辑器** | 打字、改代码，提供高亮和报错定位 | VS Code、记事本、Vim | 你没法写代码 |
| **编译器** | 把源码翻译成可执行文件 | GCC（`g++`）、Clang、MSVC | 源码只是文本，跑不起来 |

### 8.1 关键澄清：VS Code 不是编译器

这是初学者最大的误解之一。

- VS Code 只是**编辑器**（准确说是「代码编辑器」），它的本事是让打字舒服
- 它**自己不会编译**。你在 VS Code 里点「运行」时，它其实是**替你在终端敲了一条 `g++` 命令**
- 把 VS Code 卸载掉，用记事本 + 命令行照样能写出完整的 C++ 程序

### 8.2 一条完整链路上都有谁

```
   你（打字）        编辑器            编译器            链接器           CPU
   ──────────▶   VS Code 等   ──▶   g++ (前端)  ──▶  g++ (后端/ld)  ──▶  运行 exe
                     │                  │                 │
                  写 .cpp           产 .s / .o       产 .exe
```

其中「编译器」和「链接器」在 GCC 里是**同一个命令 `g++`** 在内部调用的两个不同程序——这一点在第 9 节会用命令拆开看。

### 8.3 确认自己的工具装好了

在终端里敲：

```powershell
g++ --version
```

如果打印出类似 `g++ (x86_64-win32-seh-rev0, Built by MinGW-W64 project) 8.1.0` 的信息，说明编译器就绪。如果提示「不是内部或外部命令」，说明 `g++` 没装好或者没加进系统 PATH 环境变量。

`--version` 这种以 `--` 开头的叫**命令行选项**（option/flag），作用是给命令加要求。后面会经常用到 `-std=c++17`、`-o`、`-Wall` 这些。

## 9. 【本课核心】程序创建的技巧（教材 1.4，p23–26）

### 9.1 源代码文件（1.4.1，p24）

- C++ 源文件的扩展名用 **`.cpp`**（也有人用 `.cxx`、`.cc`、`.C`）
- 源文件就是**纯文本**。编译器完全不关心你叫什么名字，只关心内容
- `.c` 是给 C 编译器看的，`.cpp` 是给 C++ 编译器看的。一个用 C 写法（`printf`）写的 `helloworld.c`，如果改名成 `.cpp` 也**照样能编译**——因为 C++ 兼容大部分 C

#### ⚠️ 一条实用规矩：**`.cpp` 文件名请用英文**

这是实测出来的，以后会天天遇到：

```powershell
# 文件名是中文的情况
g++ A_缺少分号.cpp -o A.exe
→ A_ȱ�ٷֺ�.cpp:7:38: error: expected ';' before 'return'
  ^^^^^^^^^^^^ 文件名变乱码了

# 文件名是英文的情况
g++ A_missing_semicolon.cpp -o A.exe
→ A_missing_semicolon.cpp:7:38: error: expected ';' before 'return'
  ^^^^^^^^^^^^^^^^^^^^^^ 正常
```

**为什么会这样**：GCC 在报错里是用**系统默认代码页（中文 Windows 上是 GBK/936）**输出文件名的，
而 VS Code 和一些工具是按 UTF-8 去读的，两边对不上 → 乱码。

**危害**：VS Code 靠 `文件名:行号:列号` 这个格式来自动定位错误。
文件名一乱码，它就没法把报错和你的代码行关联起来，
你就**失去了「点一下报错直接跳到出错行」这个功能**——这在以后几百行的程序里是致命的。

**结论**：

- ✅ `.cpp` / `.h` **文件名用英文**：`caesar.cpp`、`spiral_matrix.cpp`、`exercise_3.cpp`
- ✅ **文件夹名、注释、`std::cout` 输出里的中文都没问题**（这些不经过编译器报错）
- ✅ `.md` 讲义文件的中文名也没问题（VS Code 直接按 UTF-8 处理）

### 9.2 编译和链接（1.4.2，p25–26）⭐ 重中之重

教材讲得比较抽象，下面这套流程是在真实机器上**实测**跑出来的。**每一行数字都是真实结果。**

先准备一个两行的源文件 `demo.cpp`：

```cpp
#include <iostream>
int main(){ std::cout << "hi\n"; }
```

> **这两行现在看不懂很正常**，逐字解释一下备查：
> - `#include <iostream>`：把标准库里的「输入输出」功能说明**整段复制**到这里
> - `int main()`：`main` 是程序的**入口**，运行一定从它开始；`int` 表示它结束时返回一个整数
> - `{ ... }`：函数体，里面是要执行的语句
> - `std::cout << "hi\n";`：把 `hi` 打到屏幕上，`\n` 表示换行
> - 第 2 章会正式讲这些，这里只是让例子能跑

然后逐步执行，看每一步产出了什么：

#### 第 ① 步：预处理（preprocessing）

```powershell
g++ -E -std=c++17 demo.cpp -o demo.i
```

| 文件 | 大小 | 行数 |
|---|---|---|
| `demo.cpp`（你写的） | 59 字节 | **2 行** |
| `demo.i`（预处理结果） | 872,668 字节 | **29,493 行** |

**你写的 2 行，膨胀成了 29493 行。**

为什么？因为 `#include <iostream>` 的意思是：**把 `iostream` 这个文件的全部内容原样复制粘贴到这里**。而 `iostream` 又包含了别的头文件，层层嵌套，最后就是这么一大坨。

> 📌 **术语对照**：**头文件**（header file）就是那些被 `#include` 进来的文件，里面装着函数的「说明书」。**预处理器**（preprocessor）是编译最前面的一个纯文本处理程序，它只做复制、替换、删除这类文本操作，**完全不懂 C++ 语法**。

> 🔑 **这解释了新手第一困惑**：为什么 `#include <iostream>` 后面**不加分号**？
> 因为 `#include` **不是 C++ 语句**，它是给**预处理器**的命令。预处理器只是做文本替换，加不加分号它都照做，但加了分号就会在展开的内容后面留下一个孤零零的 `;`，可能引发离奇的错误。**记住：所有 `#` 开头的都是预处理指令，不写分号。**

#### 第 ② 步：编译（compilation）

```powershell
g++ -S -std=c++17 demo.cpp -o demo.s
```

得到 **汇编代码**（106 行），长这样（节选）：

```asm
main:
	pushq	%rbp
	movq	%rsp, %rbp
	leaq	.LC0(%rip), %rsi
	leaq	_ZSt4cout(%rip), %rdi
	call	_ZStlsISt11char_traitsIcEERSt13basic_ostreamIcT_ES5_PKc@PLT
	...
```

这就是「给 CPU 看的、但还是人勉强能读」的中间形态。上面这些 `pushq`、`movq`、`call` 是**汇编指令**——每一条大致对应一条 CPU 能执行的机器指令。

`_ZSt4cout` 就是 `std::cout` 被编译器改的名字（叫**名字修饰**，第 9 章会讲为什么需要它）。

> 📌 直观感受一下：源码里一句 `std::cout << "hi\n";`，到了汇编层变成了好几条 `leaq`、`call`。**这就是「高级语言离人近、离机器远」的具体含义。**

#### 第 ③ 步：汇编（assembly）

```powershell
g++ -c -std=c++17 demo.cpp -o demo.o
```

得到**目标文件** `demo.o`，**只有 1,855 字节**。

> 「汇编」这个词有两个意思，容易混：**一是汇编语言**（`.s` 里那种文本），**二是把汇编翻译成机器码这个动作**（这一步 `-c` 干的事）。这里说的是后者。

⚠️ **关键观察**：`demo.exe` 最终是 56,226 字节，而目标文件只有 1,855 字节。那少的 54KB 去哪了？

答案是：**`demo.o` 里根本没有 `cout` 的实现代码**。它只有一个「占位标记」，意思是「这里要调用一个叫 `_ZStlsISt11char_traitsIcEE...` 的东西，但我不知道它在哪，让别人来填」。

也就是说，到这一步为止，程序还是**残缺的**。

#### 第 ④ 步：链接（linking）

```powershell
g++ demo.o -o demo.exe      # 注意：这里不用再写 -std 了，因为.o已经是编译好的机器码
.\demo.exe                  # 输出 hi
```

**链接器**的工作：把 `demo.o` 和这台机器上的 **C++ 标准库**（`libstdc++`）拼在一起，把第③步那些「占位标记」填上真正的地址，最后产出 56,226 字节的完整 exe。

> **这就是「库」的意义**：`cout` 是别人（标准库作者）写好的、已经编译好的机器码。你只需要 `#include` 它的**说明书**（头文件），链接器负责把**实物**接上。
>
> 头文件 = 说明书（声明）。库 = 实物（定义）。这两件事是分开的——**这个概念不懂，你会被链接错误折磨很久。**

> 📌 「声明」和「定义」这两个词在第 12 节讲链接错误时会反复出现，先记住：
> - **声明（declaration）**：告诉编译器「有这么个东西，它叫什么、长什么样」，**不提供实现**
> - **定义（definition）**：把实现真正写出来

#### 四步一图

```
  demo.cpp          ← 你写的源码（2 行）
      │
      │  ① 预处理  g++ -E      展开 #include / #define
      ▼
  demo.i            ← 29493 行纯 C++ 代码
      │
      │  ② 编译    g++ -S      C++ → 汇编
      ▼
  demo.s            ← 106 行汇编
      │
      │  ③ 汇编    g++ -c      汇编 → 机器码
      ▼
  demo.o            ← 1855 字节目标文件（有洞，未填）
      │
      │  ④ 链接    g++        把标准库拼上、填洞
      ▼
  demo.exe          ← 56226 字节，能跑了
```

想一次性留下所有中间文件，加 `--save-temps`：

```powershell
g++ --save-temps -std=c++17 demo.cpp -o demo2.exe
```

然后你会看到 `demo.i`、`demo.s`、`demo.o` 全在目录里。

> **平时不用管这些**，`g++ demo.cpp -o demo.exe` 一步就全做了。但你必须知道**背后发生了这四件事**——因为出错时，你得知道该怪哪一步。

#### 补充：一个 6 行版本的真实数字，供对照

上面那个 2 行的例子是为了说明「膨胀」有多夸张。实际动手时你通常会写一个更完整的版本：

```cpp
#include <iostream>
int main()
{
    std::cout << "我在测试编译过程" << std::endl;
    return 0;
}
```

这个版本在一台真实机器（GCC 8.1.0, MinGW-W64, Windows）上的实测值是：

| 文件 | 实测值 |
|---|---|
| `demo.cpp` 行数 / 字节数 | 6 行 / 111 字节 |
| `demo.i` 行数 / 字节数 | **21,519 行** / 872,724 字节 |
| `demo.s` 行数（汇编） | **115 行** |
| `demo.o` 字节数（目标文件） | 2,354 字节 |
| `demo.exe` 字节数（可执行文件） | 56,837 字节 |

**注意两个反直觉的点**：

1. **`.s` 汇编文件的行数会随版本和优化选项大幅变化**：上面的最小例子是 106 行，这个 6 行版本是 115 行。**行数不是重点，重点是「C++ 被拆成了很多条机器指令」这个事实。**
2. **`.o` 到 `.exe` 增长了约 54KB**，稳定复现——这就是链接标准库带进来的体积。

## 10. 【本课第二个核心】三类错误 —— 拿到报错先分类

下面是实测出来的几种报错。**以后每次看到红色报错，第一件事是判断它属于哪一类**，因为不同类错误的排查方向完全不同。

### 类型 A：编译错误（compile-time error）—— 语法/类型问题

源码（漏了一个分号），放在 `示例代码/01_错误分类实验/A_missing_semicolon.cpp`：

```cpp
#include <iostream>
int main()
{
    std::cout << "hello" << std::endl      // ← 这里少一个分号
    return 0;
}
```

真实报错：

```
A_missing_semicolon.cpp: In function 'int main()':
A_missing_semicolon.cpp:4:38: error: expected ';' before 'return'
     std::cout << "hello" << std::endl
                                      ^
                                      ;
     return 0;
     ~~~~~~
```

**教你怎么读这条消息**（这个技能值一整章）：

| 这一部分 | 意思 |
|---|---|
| `A_missing_semicolon.cpp: In function 'int main()'` | 错误发生在 `main` 函数里 |
| `A_missing_semicolon.cpp:4:38` | **文件名 : 第 4 行 : 第 38 列** ← 先看这个定位 |
| `error:` | 这是**错误**（`warning:` 是警告，稍后讲） |
| `expected ';' before 'return'` | 编译器说：在 `return` 前面我应该看到一个 `;`，但没有 |
| `^` 和下面的 `;` | GCC 好心画的：指出位置，并**把缺的分号补给你看** |
| `~~~~~~` | 波浪线，标出它觉得相关的另一段代码 |

⚠️ **新手最常见的误读**：报错说 `expected ';' before 'return'`，很多人在 `return` 那一行找问题。**错。** 编译器是在读到 `return` 的时候才发现前面缺东西，真正的错误在**上一行的末尾**。记住：**报错行号常常指在错误的下一行。**

**特征**：编译错误**不会生成 exe**（实测验证过，`A_missing_semicolon.exe` 根本不存在）。所以「编译报错」和「程序崩了」是完全不同的两件事。

### 类型 B：链接错误（link-time error）—— 声明了，但找不到实现

源码，放在 `示例代码/01_错误分类实验/B_undefined_function.cpp`：

```cpp
#include <iostream>
int add(int a, int b);          // 只有"声明"，没有"定义"（函数体）
int main()
{
    std::cout << add(1, 2) << std::endl;
    return 0;
}
```

真实报错：

```
...ccdos0Ve.o:B_undefined_function.cpp:(.text+0x18): undefined reference to `add(int, int)'
collect2.exe: error: ld returned 1 exit status
```

**关键词是 `undefined reference`（未定义的引用）**。翻译成人话：

> "`add` 这个名字我见过（你在第 2 行声明过），但我翻遍了所有目标文件和库，**找不到它的函数体**。"

**排查方向**：

1. 函数是不是只写了声明（`int add(int,int);`）忘了写定义（带 `{}` 的那部分）？
2. 定义是不是写在别的 `.cpp` 文件里，但编译时**没把那个文件也加进去**？（第 9 章会讲多文件编译）
3. 函数名/参数类型是不是和声明不一致？（C++ 会区分 `add(int,int)` 和 `add(double,double)`）

**注意**：链接错误里出现的是 `collect2.exe` / `ld`，这是**链接器**，不是编译器。看到 `ld` 就知道是第④步出的问题。

**正确写法**（补上函数体）：

```cpp
int add(int a, int b)
{
    return a + b;
}
```

### 类型 C：编译错误（类型不匹配）

源码，放在 `示例代码/01_错误分类实验/C_type_mismatch.cpp`：

```cpp
#include <string>
int main()
{
    std::string s = 12345;      // 想用整数初始化 string
    return 0;
}
```

真实报错：

```
C_type_mismatch.cpp:4:21: error: conversion from 'int' to non-scalar type
'std::__cxx11::string' {aka 'std::__cxx11::basic_string<char>'} requested
```

- `conversion from 'int' to ... requested`：不允许从 `int` 转换到 `string`
- `{aka 'std::__cxx11::basic_string<char>'}`：`aka` = "also known as"，真实类型叫 `basic_string<char>`，`string` 只是个别名。**这个 `__cxx11` 前缀是 GCC 的旧 ABI 命名**，看到它不要慌，它就是在说「字符串类型」

> 💡 **先说明一个容易混淆的点**：下面的「**类型 A / B / C / D / E**」是**错误的分类**；
> 而 `示例代码/01_错误分类实验/` 里那些文件名的首字母（A/B/C/D/E/F）只是**标本编号**，
> 两套编号**不是一一对应的**。读的时候以「类型」为准。
> 📌 类型 A 和类型 C 都属于**编译错误**（都在第 ①② 步被抓住），只是一个错在**语法**（少符号），一个错在**类型**（类型不兼容）。报告里都带 `error:` 和行号，处理方式一样：**去看报错定位的那一行或它的上一行**。

### 类型 D：运行时错误（runtime error）—— 最难查的一类

能编译、能链接、能生成 exe，**跑起来结果不对或直接崩**。

**凯撒密码的经典 bug 就是这一类**：把每个字母往后推 3 位，输入 `abc` 输出 `def`（看着没问题），输入 `XYZ` 却输出 `[\]`。编译器完全帮不了你，因为代码在语法和类型上都没错——**错在逻辑**。

> 为什么会这样：字母在计算机里用编号表示，`'X' + 3` 得到的不再是字母，而是字母表之外的字符。**这个 bug 的修复版在 `示例代码/01_参考_代码重构示例/caesar_fixed.cpp`。** 建议先自己想修复方案，再看别人的——直接看会浪费掉一次很好的学习机会。

这类错误只能靠：**测试**（尤其是边界测试）、**调试器**、**打印中间变量**。

> 💡 **什么叫「边界测试」**：不要只测中间的、好想的情况。测第一个、最后一个、空的、最大的、最小的、重复的。上面这个 bug 就是「只测了小写中间段、没测末尾字母」导致的。

### 类型 D2：运行时错误里最危险的一种 —— 不崩溃但结果是错的

**这类错误值得单独拎出来讲**，因为它的杀伤力最大。

实测样本 `示例代码/01_错误分类实验/E_array_out_of_bounds.cpp`：

```cpp
#include <iostream>
int main()
{
    int a[3] = {1, 2, 3};
    for (int i = 0; i <= 3; ++i)   // 注意是 <= 3
    {
        std::cout << a[i] << " ";
    }
    std::cout << std::endl;
    return 0;
}
```

真实结果：

| 项目 | 结果 |
|---|---|
| 编译器输出 | **什么都没有**（`-Wall -Wextra` 也没警告！） |
| 生成 exe | **成功** |
| 程序输出 | `1 2 3 3 ` |
| 退出码 | **0（正常结束！）** |

**请仔细看这个结果：**

- `a` 只有 3 个元素，但循环访问了 `a[0]` `a[1]` `a[2]` **`a[3]`**
- `a[3]` 是**越界**的，它属于别的变量（甚至是别的函数的内存）
- 程序**没有崩溃**，**退出码 0**，输出 `1 2 3 3`
- 那个多出来的 `3` 是**内存里的垃圾数据**，这次恰好是 3，下次可能是一千万，也可能是负数

**这就是 C++ 最坑的地方**：

> **C++ 默认不检查数组越界。** 它相信你写的下标是对的，直接把「`a` 的起始地址 + 3×4 字节」那个位置的内存给你。
> 这个行为叫 **未定义行为（undefined behavior, UB）** —— 标准里说「这种情况下的行为不做任何保证」。
> 它可能：正常跑出错误结果 / 崩溃 / 有时对有时错 / 在某些编译器上跑得「看起来正常」。**全都是「合法」的。**

**为什么这一类比「直接崩溃」危险**：

- 崩溃了 → 你**知道**出问题了，会去查
- 不崩、退出码 0、看着像正常输出 → 你**以为**没问题，然后程序把错误的数据写进了文件或数据库

**怎么防**：

1. 老老实实写 `i < size`，别写 `<=`
2. 用 `std::vector` 并用 `.at(i)` 访问（越界会抛异常；`[]` 不检查）
3. 打开编译器的检查开关（第 4 章讲指针时会教 `-fsanitize=address`）
4. **写测试，把边界情况都试一遍**

### 类型 D3：运行时崩溃 —— 整数除以 0

实测样本 `示例代码/01_错误分类实验/D_divide_by_zero.cpp`：

```cpp
#include <iostream>
int main()
{
    int a = 10;
    int b = 0;
    std::cout << "程序开始运行" << std::endl;
    std::cout << "10 / 0 = " << a / b << std::endl;
    std::cout << "这一行会被打印吗？" << std::endl;
    return 0;
}
```

真实结果：

| 项目 | 结果 |
|---|---|
| 编译器输出 | **什么都没有**（`-Wall -Wextra` 也没警告） |
| 生成 exe | **成功** |
| 程序输出 | 只有 `程序开始运行` 一行 |
| 退出码 | **-1073741676** |

**两个关键点：**

1. **`这一行会被打印吗？` 没有被打印** —— 说明程序在 `a / b` 那一行**直接崩掉了**，后面的代码一行都没执行。
2. **退出码 `-1073741676` 是什么？**
   换成十六进制是 `0xC0000094`，这是 Windows 的错误码 `STATUS_INTEGER_DIVIDE_BY_ZERO` —— **整数除零异常**。
   （顺便记住：退出码 0 = 正常结束；**非 0 = 出问题了**。以后程序「没输出」的时候，先看退出码。）

> **为什么编译器和 `-Wall -Wextra` 都没发现？**
> 因为 `a` 和 `b` 是变量，**编译器在编译期不知道 `b` 的值是 0**。它没法预知。
> 这类「值在运行时才确定」的错误，编译器永远帮不了你——**这就是为什么你需要自己写测试**。

### 类型 E：警告（warning）—— 不阻止你，但必须处理

实测样本 `示例代码/01_错误分类实验/C_extra_semicolon.cpp`：`#include` 后面多加了一个分号。

```cpp
#include <iostream>;
int main()
{
    std::cout << "能跑吗" << std::endl;
    return 0;
}
```

真实输出：

```
C_extra_semicolon.cpp:6:20: warning: extra tokens at end of #include directive
 #include <iostream>;
                    ^
```

- 生成 exe 了吗？**生成了！** 而且程序正常运行，输出「能跑吗」，退出码 0

**所以「`#include` 后面不能加分号」这句话的准确版本是**：

- 加了分号**不会报错**，程序照样跑
- 但编译器会**警告** `extra tokens at end of #include directive`（「该指令末尾有多余的记号」）
- 所以要**养成不加分号的习惯**——不是因为会崩，而是因为这是错的写法，在别的编译器上可能就真报错了

> 📌 **顺便注意行号**：报错说第 **6** 行，可 `#include` 明明在第 1 行。
> 因为 `#include` 是**预处理指令**，第①步展开后你的代码在预处理结果里跑到第 6 行了。GCC 很聪明，它同时知道两种位置，这里报的是展开后的位置。
> **看到行号和你的文件对不上时，先想想是不是预处理（`#include`/`#define`）导致的。**

> 💡 **`warning:` 和 `error:` 的区别**：`error` 会让编译**停止**，不产出 exe；`warning` 会**继续编译**，产出 exe。但**警告往往就是未来的 bug**——尤其在有几百行代码的项目里，一个「小警告」通常正是问题的起点。养成「警告也当错误处理」的习惯。

### 错误分类汇总表

| 实验 | 属于哪一步 | 生成 exe? | 关键词 | 怎么排查 |
|---|---|---|---|---|
| A 缺分号 | **编译期** | ❌ | `error: expected ';' before ...` | 看报错行的**上一行** |
| B 函数未定义 | **链接期** | ❌ | `undefined reference to` / `ld returned` | 查函数定义、查参与编译的文件 |
| C 类型不匹配 | **编译期** | ❌ | `error: conversion from ... requested` | 看类型是否写对 |
| D 除以 0 | **运行期** | ✅ | 退出码 `-1073741676` | 崩了 → 看退出码 + 定位到出错行 |
| E 数组越界 | **运行期** | ✅ | **无任何提示** | 最危险，只能靠测试和工具 |
| F `#include;` | 预处理期（仅警告） | ✅ | `warning: extra tokens` | 只是不规范，但养成好习惯 |

### 三类错误排查口诀

> 有 exe 吗？
> - **没有** + 报错里有 `error:` 和行号 → **编译错误** → 去看那一行的**上一行**
> - **没有** + 报错里有 `undefined reference` / `ld returned` → **链接错误** → 去查函数定义和参与编译的文件
> - **有** exe 但结果不对 → **运行时错误** → 去写测试、打断点

## 11. 关于中文乱码：一个正确且漂亮的方案

在 Windows 上写中文输出的程序，很容易遇到乱码。下面这个头文件方案是**正确且漂亮**的，解释一下原理，之后你就能自己判断：

```cpp
#if defined(_WIN32)              // 只在 Windows 上编译这段
#include <windows.h>
__attribute__((constructor))     // GCC 扩展：让这个函数在 main() 之前自动执行
static void utf8_console_activate(void)
{
    SetConsoleOutputCP(65001);   // 把控制台输出代码页改成 UTF-8
    SetConsoleCP(65001);         // 输入代码页也改，这样 scanf/cin 读中文也正常
}
#endif
```

三个要点：

1. **`__attribute__((constructor))`** 是 GCC 的扩展，它让这个函数**在 `main()` 之前自动运行**。所以源码里不需要调用任何东西，`#include` 就生效了。
2. **`SetConsoleOutputCP(65001)`** 是把 Windows 控制台的「代码页」从默认的 936（GBK）改成 65001（UTF-8），这样程序输出的 UTF-8 字节就能被正确显示。
3. **为什么需要它**：VS Code 里那个 UTF-8 修复（`[Console]::OutputEncoding`）只对**从 VS Code 终端启动的程序**有效；一旦你双击 exe，就是在普通的 GBK 控制台里跑，又会乱码。这个头文件把两种情况都覆盖了。

> 📌 **「代码页」是什么**：就是一张「字节 ↔ 字符」的对照表。同一个字节，按 GBK 表查是一个汉字，按 UTF-8 表查可能是别的东西。乱码的本质就是**写的一方和读的一方用了不同的表**。

**要不要用**：写学习练习时**可以不加**（在 VS Code 里跑本来就正常）。等你要双击运行 exe 给别人看的时候再加。

```cpp
#include <iostream>

```

然后：

```powershell
# ① 预处理
g++ -E -std=c++17 demo.cpp -o demo.i
(Get-Content demo.i).Count              # 看有多少行

.\demo.exe

# 一次性看全部中间文件

Get-ChildItem
```

## 14. 常见坑汇总

这一章的内容本身不难，但下面这些坑几乎人人踩过。**建议把这一节单独抄下来贴在显示器边上。**

### 14.1 概念类坑

| # | 坑 | 正确认识 |
|---|---|---|
| 1 | 以为 VS Code 是编译器 | VS Code 只是**编辑器**，真正翻译代码的是 `g++` |
| 2 | 以为 `#include` 是 C++ 语句 | 它是**预处理指令**，不是语句，**不加分号** |
| 3 | 以为头文件里装着实现代码 | 头文件是**说明书（声明）**，实现（定义）在库或别的 `.cpp` 里 |
| 4 | 以为「编译通过」= 程序对 | 编译只检查语法和类型，**逻辑错误它一概不管** |
| 5 | 以为「改了源码 = 程序变了」 | 必须**重新编译**，否则跑的还是旧 exe |
| 6 | 以为 `.o` 文件是「小一点的 exe」 | 它**有洞**，缺函数实现，单独不能跑 |
| 7 | 以为中文文件名编译器也能正确报错 | GCC 报错按系统代码页输出文件名，**`.cpp`/`.h` 一律用英文名** |
| 8 | 以为 C++ 的可移植是「exe 到处跑」 | 是**源码到处重新编译**，不是同一个 exe |

### 14.2 操作类坑

| # | 坑 | 怎么避免 |
|---|---|---|
| 9 | 在错的目录里敲命令，报「找不到文件」 | 敲命令前先 `pwd` 确认当前位置 |
| 10 | 路径里有空格不加引号 | `cd "C:\My Projects"` |
| 11 | 直接敲 `demo.exe` 说「无法识别」 | PowerShell 里要写 `.\demo.exe` |
| 12 | 忘了 `-o`，结果可执行文件变成默认名 | 命令里始终写清 `-o 名字.exe` |
| 13 | 用 `-std` 链接 `.o` 时多余恐慌 | 链接 `.o` 时不需要也不影响 `-std` |

### 14.3 排错类坑

| # | 坑 | 正确做法 |
|---|---|---|
| 14 | 报错说 `expected ';' before 'return'`，就去 `return` 行找 | 真正的错误**几乎总在上一行末尾** |
| 15 | 看到报错行号和自己的文件对不上，怀疑编译器坏了 | 先想 `#include`/`#define` 展开导致的行号偏移 |
| 16 | 看到 `undefined reference` 却去改语法 | 这是**链接**错误，去查函数定义和编译命令里漏掉的文件 |
| 17 | 看到 `collect2.exe` / `ld` 以为是编译器坏了 | 那是**链接器**在报错，问题在第 ④ 步 |
| 18 | 忽略 `warning:`，觉得「反正能跑」 | 警告往往就是未来的 bug，**当错误处理** |
| 19 | 程序没输出就反复改代码 | 先**看退出码**：非 0 说明运行期崩了 |
| 20 | 数组越界没崩，就以为代码是对的 | 越界是**未定义行为**，这次侥幸不代表正确 |
| 21 | 只测「正常输入」 | 必须测**边界**：空、1 个、最后一个、最大/最小 |
| 22 | 看到 `std::__cxx11::basic_string<char>` 这种长名字就慌 | 那只是 `std::string` 的**真实名字**，`aka` 后面才是别名 |
